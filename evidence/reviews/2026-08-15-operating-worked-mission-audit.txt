## 독립 감사 판정: **미통과**

운영 원칙은 대체로 잘 갖춰져 있습니다. 그러나 `export-ownership` 대표 미션은 실제 자료와 상태가 이어지는 서사가 아니라, 추상 절차와 필드 목록을 예시에 덧씌운 수준입니다. 따라서 사용자가 요구한 **요청부터 변경·`STALE` 처리까지의 종단 추적성**은 충족하지 못합니다.

### 확인된 강점

- 세 책임 축의 목적·입출력·금지 행위가 구분되어 있음: `docs/architecture/operating-model.md:5-35`
- 세 축이 요구 단계에서 품질 계획을 공동 작성함: `operating-model.md:51-70`, `docs/expert-organization-design.md:246-280`
- 관점 생성 → P0~P5 배정 → 세 층 지식 → 독립성에 따른 전문가 분리 순서가 명확함: `operating-model.md:72-128`, `expert-organization-design.md:80-205`
- 자동 인계 검사와 수신자의 사용 가능성 판단을 분리함: `operating-model.md:130-150`, `expert-organization-design.md:223-244`
- 총괄 관리자의 구현·검증·자가 승인·패키징 금지는 명시됨: `expert-organization-design.md:67-78`

## 주요 누락

### 1. `[중대]` 대표 미션이 이름만 구체적이고 실행 자료는 추상적임

- 요청은 한 문장뿐임: `docs/architecture.md:64-68`, `docs/architecture/runtime.md:7-13`
- `runtime.md:17-109`는 9단계 순서를 제공하지만, 3단계 이후에는 거의 모두 일반적인 구성 요소 설명임.
- 동일한 `mission_id`, revision, 단계 상태, 작업 ID, 권한 ID, 후보본 ID, 증거 ID가 다음 단계로 이어지지 않음.
- 전이 전 상태 → 입력 자료 → 검사 결과 → 전이 후 상태를 보여 주는 사건이 한 건도 없음.

따라서 독자는 “이 기능의 어떤 자료가 어떤 판정을 거쳐 어느 상태가 되었는가”를 재구성할 수 없습니다.

### 2. `[높음]` 목표 충분성 판정과 총괄 관리자의 계획 산출물이 빠짐

- 대표 미션 흐름에는 목표 충분성 판정이 없음.
- 유일한 언급은 구성 요소 책임 목록의 `checks goal sufficiency`뿐임: `runtime.md:122-127`
- 총괄 관리자는 조정자로 설명됨: `operating-model.md:37-49`, `expert-organization-design.md:67-78`
- 그러나 목표 충분성, 단계, 전문가, 위험, 증거, 통과 기준을 하나의 revision별 계획으로 구성한다는 계약은 없음.
- `Goal and Quality Planner`와 `Mission Manager`가 각각 어디까지 책임지는지도 분명하지 않음.

또한 canonical 운영 모형의 금지 목록인 `operating-model.md:41-47`에는 “후보본 검토·검증을 수행하지 않는다”가 직접 적혀 있지 않습니다. 이 금지는 다른 문서에만 있습니다.

### 3. `[높음]` 단계 계약이 없음

- 공동 계획에서 “단계 입력·출력·증거”를 정한다고만 함: `operating-model.md:51-64`
- 권한과 정책 검사는 계속 `stage`를 참조함: `runtime.md:44-54`, `runtime.md:183-197`
- 하지만 단계 이름, 상태 순서, 단계별 책임자, 필수 입력·출력, 통과 기준, 실패 복귀 지점이 정의되지 않음.

현재 문서의 “Step 1~9”가 실제 권한과 상태 기계가 사용하는 “stage”인지도 알 수 없습니다.

### 4. `[높음]` 동적 전문가 구성 규칙은 있으나 실제 구성 결과가 없음

- 관점과 P 수준의 예시는 있음: `runtime.md:33-42`
- 그러나 `export-ownership`에 실제로 구성된 전문가 명단은 없음.
- 각 전문가의 세 층 지식, 담당 관점, 책임 축, 단계, 산출물, 독립성, 권한과 작업 공간이 제시되지 않음.
- `expert-organization-design.md:134-205`도 구성 규칙만 있고 하나의 완성된 적용 사례가 없음.

특히 P3 보안 전문가와 P4 독립 QA가 같은 사람·모델·권한·작업 공간을 공유하지 않는다는 결과를 확인할 수 없습니다.

### 5. `[중대]` 후보본부터 출시까지 자료와 판정 결과가 없음

다음 항목은 모두 필요한 필드를 나열할 뿐, 대표 미션의 실제 기록을 보여 주지 않습니다.

- 권한 증표: `runtime.md:44-56`
- 작업 공간과 실행 영수증: `runtime.md:58-70`
- 후보본과 manifest: `runtime.md:72-83`
- 자동 인계 검사와 수신자 수락: `runtime.md:85-89`
- 독립 QA와 finding: `runtime.md:91-103`
- 출시 판정과 패키징: `runtime.md:105-109`

최소한 다음 값이 한 흐름으로 필요합니다.

- 발급된 권한의 대상·허용 명령·쓰기 경로·만료·사용 횟수
- Engineering과 QA의 분리된 작업 공간 및 QA의 읽기 전용 후보본 경로
- 후보본 ID, 부모 ID, revision, manifest hash, 입력 파일 경로·해시, `FROZEN` 상태
- 인계 생산자·수신자·산출물·자동 검사 결과·수신자 수락 사유
- QA 명령, fixture, 예상값, 관찰값, 종료 코드, 증거 ID
- 품질 항목별 하한 판정, 잔여 위험, 최종 출시 범위와 상태

### 6. `[중대]` 변경 → 자식 후보본 → `STALE` 전파 서사가 없음

- 보안 실패 시 자식 후보본을 만든다는 한 문장만 있음: `architecture.md:70-76`
- 변경 시 새 revision 또는 `STALE`이 된다는 일반 원칙만 있음: `architecture.md:88-98`
- 런타임에서도 관련 기능이 구성 요소 책임으로 흩어져 있음: `runtime.md:17-20`, `runtime.md:115-120`, `runtime.md:129-135`, `runtime.md:154-159`

빠진 내용은 다음과 같습니다.

- 무엇이 바뀌었는지
- 같은 revision의 후보본 수정인지, 사용자 지시에 따른 새 revision인지
- 새 후보본의 `parent_candidate_id`
- 어떤 기준선·인계·시험·QA·출시 판정이 `STALE`인지
- 영향을 받지 않아 재사용 가능한 증거는 무엇인지
- 정책이 구 증거를 이용한 패키징을 어떻게 거부하는지
- 재검증 뒤 최종 상태가 무엇인지

## 완료 판정 기준

수정된 대표 미션은 각 단계마다 최소한 다음 형식을 가져야 합니다.

> **이전 상태 → 입력 자료와 ID → 책임자와 권한 → 실제 검사·판정 근거 → 생성된 자료 → 다음 상태**

그리고 처음부터 끝까지 동일한 `mission_id`와 계보가 유지되어야 합니다.
