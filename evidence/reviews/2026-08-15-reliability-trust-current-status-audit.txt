## 감사 판정: **보류(HOLD)**

복구 시나리오와 신뢰 한계의 개념 설명은 상당히 충실합니다. 특히 최신 `reliability.md`는 체크포인트 전·후 중단, 동일 논리 작업의 새 시도, 외부 효과 대조·보상, 검증자 이견, 완료 후 무효화를 같은 예시 미션에 연결합니다. 그러나 **완료 증거의 원자적 결속, 적대적 거부 사례, 현재 상태의 스냅샷 증명**이 부족합니다. 현재 구현에서는 실행하지 않은 `pass`도 역할 문자열만 바꿔 직접 핵심 API에서 `APPROVED`로 만들 수 있었습니다.

### 주요 발견

1. **[치명적] 완료 조건이 나열돼 있을 뿐 하나의 검증 가능한 증거 봉투로 결속되지 않는다.**
   - `docs/architecture/reliability.md:15-24`는 권한, 실행 기록, 산출물, 해시, revision, 후보본을 별도 조건으로 열거합니다.
   - `docs/architecture/trust.md:34-40`은 “결속한다”고만 하고 결속 레코드의 필수 필드·검증 순서를 정의하지 않습니다.
   - `docs/architecture/reference.md:33-41`에는 독립된 **Evidence/Verification Attestation 레코드 가족**이 없으며, 실행 레코드에도 권한 발급·소비 사건, 실행기 신원, 명령·환경·종료 코드, 산출물 SHA-256을 하나로 묶는 계약이 없습니다.
   - 실제 구현의 증거 레코드도 `src/agent_harness/evidence.py:21-35`처럼 `task_id`, `attempt_id`, 권한 ID, 실행기 신원, 명령·환경·종료 코드가 없습니다.
   - **필요한 보완:** 미션·revision·task·attempt·candidate·발급 권한·실행기·생산자 역할·명령/환경·종료 코드·실제 파일 SHA-256을 한 증거 봉투에 넣고, 역할을 호출자 문자열이 아니라 권한에서 유도한다고 명시해야 합니다.

2. **[치명적] 현재 핵심 API는 역할 문자열과 자가 주장 `pass`만으로 승인이 가능하다.**
   - `src/agent_harness/plugin_service.py:268-312`는 호출자가 낸 `producer_role`과 `outcome`을 받고, `:330-379`는 호출자가 낸 `reviewer_role`로 승인합니다.
   - `src/agent_harness/policy.py:65-100`은 역할 문자열의 등록 여부와 문자열 간 불일치만 검사합니다.
   - 독립 probe에서 한 호출자가 후보 작성자·검증자·승인자 역할 문자열을 모두 제출하고, 실제 명령은 실행하지 않은 채 임의 JSON 파일을 `pass` 증거로 넣어 `approved` 상태를 얻었습니다.
   - `docs/architecture/current-status.md:69-74`가 이 계열의 결함을 방향상 올바르게 인정하지만, **“실제 실행 없이 승인 가능”이라는 관찰된 보안 결과와 재현 근거**는 기록하지 않습니다.

3. **[높음] 요구된 적대적 거부 사례가 하나의 판정표로 완결되지 않았다.**
   - 역할 문자열 사칭: 원칙만 있음 — `trust.md:36`
   - 자가 `pass`: 독립 검증을 대체할 수 없다고만 함 — `reliability.md:39`
   - 구 revision: 일반 조건만 있음 — `reliability.md:24`, `trust.md:42`
   - 후보 변경 후 옛 증거: 자식 후보와 재검증 원칙은 있으나 명시적 거부 전이가 없음 — `reliability.md:100-105`
   - 자가 승인: 분리 원칙·목표 테스트 이름만 있음 — `trust.md:41`, `reference.md:97`
   - 누락 산출물: 완료 조건만 있음 — `reliability.md:17-19`
   - 심볼릭 링크 탈출: 현재 격차와 목표 테스트 이름만 있음 — `current-status.md:52,75`, `reference.md:94`
   - 각 사례마다 **입력, 거부 이유, 상태 불변, 감사 사건, 재시도 가능 여부**를 적어야 합니다. `reference.md:86-100`은 이를 “중요한 목표 테스트 그룹”으로만 나열하므로 현재 통과 증거로 읽을 수 없습니다.

4. **[높음] 외부 효과 중복 제거 키의 안정성이 모호하다.**
   - 최신 `reliability.md:43-57,75-80`은 논리 작업·시도와 안정적인 논리 작업 ID를 잘 구분합니다.
   - 그러나 `agent-reliability-survey.md:52-58`은 각 작업 시도에 `invocation_id`와 `attempt_id`를 부여하고, `:78-84`의 중복 제거 키에는 `invocation_id`를 포함합니다.
   - `invocation_id`가 시도마다 바뀐다면 재시도 때 키도 바뀌어 중복 제거가 깨집니다. 안정적인 논리 작업/효과 ID인지, 시도 ID인지 명확히 구분하고 **attempt ID는 외부 효과 중복 제거 키에서 제외**해야 합니다.

5. **[중간] LLM 검증자 편향 설명은 충실하지만 강제 가능한 계약과 현재 상태가 없다.**
   - 순서 효과, 장황성 선호, 자기 선호, 같은 모델 계열의 비독립성, 항목별 평가, A/B 순서 교환, 판정 반전 시 자동 승인 금지, 이질 모델, 실행 오라클은 잘 설명돼 있습니다: `reliability.md:152-167`, `trust.md:78-92`, `agent-reliability-survey.md:136-187`.
   - 하지만 `reliability.md:165`가 말하는 비교 레코드에 대응하는 스키마가 `reference.md:58-68`에 없고, `current-status.md:58`도 이를 포괄적인 “Dynamic quality decision” 목표로만 처리합니다.
   - 모델·프롬프트·평가 항목·제시 순서·교환 판정·신뢰도·이견·`INCONCLUSIVE/HOLD` 전이를 담는 레코드와 구현 상태가 필요합니다.

6. **[높음] 현재 상태 문서가 자기 상태를 안정된 스냅샷에 결속하지 못한다.**
   - `current-status.md:9-15`에는 시각·브랜치만 있고 commit, 후보본 ID, 트리/index 지문이 없습니다.
   - 테스트 결과 `:17-42`에도 원시 로그 산출물 경로·SHA-256과 대상 소스 지문이 없어 현재 파일과 같은 실행인지 재검증할 수 없습니다.
   - `:67`의 “latest known independent review” 역시 리뷰 ID, reviewer 권한, revision, candidate, 보고서 SHA-256이 없습니다.
   - `:81-89`는 상태 변경에 후보본·산출물 해시를 요구하면서 정작 현재 상태 자체에는 이를 제공하지 않습니다.
   - 실제 재실행에서는 문서와 동일하게 **5 failed, 50 passed, exit 1**이 나왔지만, 이는 개수만 재확인했을 뿐 문서의 실행과 동일한 스냅샷임을 증명하지 않습니다.

7. **[중간] OS·외부 서비스 한계 구분은 좋지만 실제 통제 현황표가 없다.**
   - 목표 하네스와 OS 통제의 차이는 `trust.md:30-61`, 외부 서비스 한계는 `:63-76`에서 명확히 구분합니다.
   - 그러나 `trust.md:61`의 “관찰된 경우에만 존재를 기술한다”는 약속과 달리 `current-status.md`에는 OS 계정, ACL, 읽기 전용 마운트, 네트워크, 자격 증명, 외부 서비스의 중복 제거·조회 지원을 **관찰/미관찰/범위 밖**으로 나눈 표가 없습니다.
   - 심볼릭 링크 거부와 같은 하네스 검사와 동일 계정의 TOCTOU 경합이라는 OS 잔여 위험도 같은 항목에서 대조해야 합니다.

8. **[중간] 현재 구현과 목표를 다시 섞을 수 있는 규범 우선순위가 있다.**
   - `reference.md:124`는 요구·스키마·테스트·ADR이 설명 문서보다 우선한다고 합니다. 현재 스키마와 테스트가 불완전하고 종단 흐름도 실패하는 상태(`current-status.md:28-42`)이므로, 구현 산출물인 테스트·스키마가 목표 아키텍처를 역으로 덮을 수 있습니다.
   - 규범은 승인된 요구 기준선과 ADR이어야 하며, 스키마·테스트는 특정 revision/candidate에 결속된 적합성 증거로 두는 편이 안전합니다.
   - `agent-reliability-survey.md:273-285`의 “사용자와 합의”, “확정했다”도 승인 기준선 ID·revision·결정 기록 없이 합의 완료를 주장합니다. 거짓이라고 단정할 수는 없지만 현재 문서만으로는 입증되지 않습니다.
