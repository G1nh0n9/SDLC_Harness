## 독립 감사 결과

**종합 판정: 중대한 보완이 필요합니다.**  
문서는 역사적 판본 이력이 아니라 공학적 계보를 다루려는 방향은 맞지만, 요구된 reference model을 **모델별로 완결되게 설명하지 못했습니다.** 특히 다음 두 가지가 결정적입니다.

1. **증거 중심 완료 판정의 역사적 모델이 없습니다.**
2. 출처가 해당 원리를 설명한다는 사실과, 그 원리가 실제로 하네스 설계에 영향을 미쳤다는 사실을 구분하지 않습니다.

인용 번호 29–43은 원장과 모두 일치했고, 누락되거나 사용되지 않은 원장 항목은 없었습니다. 그러나 이는 URL 대응만 확인할 뿐, 문단별 주장을 입증하지는 못합니다.

## 문단별 주요 발견

### 문서의 전제와 약속

- **`docs/architecture/historical-foundations.md:3-5` — 영향 관계 과장 가능성.**  
  “shaped this harness”, “engineering lineage”, “combines reference models”는 실제 설계 당시 해당 원전을 채택했다는 인과적 표현입니다. 그러나 설계 기록, ADR, 채택 시점, 저자 진술이 없습니다. 현재 자료로 입증되는 것은 대부분 **사후 비교 또는 개념적 유사성**입니다.

- **`historical-foundations.md:7-12` — 자체 완결성 약속 불이행.**  
  1–9절에는 네 개의 정형 문단이 각각 한 번씩 있지만, 여러 모델을 한 절에 묶었습니다. 10절에는 네 문단 자체가 없습니다. 따라서 “각 tradition마다” 네 항목을 구분한다는 약속을 충족하지 못합니다.

- **역사성 자체가 얕습니다.**  
  문서 전체에 발표 연도, 당시 개발 관행, 후속 발전, 모델 간 선후 관계가 거의 없습니다. “historical foundations”라기보다 현재 설계와 기존 개념을 대조한 목록에 가깝습니다.

### Fagan inspection

- **`historical-foundations.md:28` — 핵심 절차를 지나치게 압축.**  
  준비·결함 발견·수정·후속 확인은 나오지만, Fagan inspection의 역할 분리, 계획·개요·검사 회의, 검사 속도, 결함 분류와 계량은 빠졌습니다.

- **`:30-32` — 일반적인 리뷰 원칙으로 평탄화.**  
  “informal review misses defects”, “prepared reviewers”, “reproducible findings”는 타당하지만, 왜 이것이 일반 동료 검토가 아니라 Fagan 모델의 계승인지 드러나지 않습니다.

- **`:34` — 출처와 무관한 내용 혼입.**  
  immutable candidate는 적절한 하네스 변형이지만, “receiving specialist”의 handoff usability 판단은 Fagan 계승인지 별도 하네스 원칙인지 구분되지 않습니다.

- **`:36` — 미채택 설명이 허수아비 논증에 가깝습니다.**  
  Fagan이 회의·서명·합의를 correctness proof로 간주했다는 근거는 제시되지 않습니다. 실제로 미채택한 역할 체계, 검사 회의, 계량 방식 등을 밝혀야 합니다.

### 시스템공학과 검증/유효성 확인

- **`historical-foundations.md:40` — 시스템공학과 V&V가 한 문장에 병합됨.**  
  NASA 프로세스 나열은 정확한 방향이지만, verification이 해결한 “명세 불일치”와 validation이 해결한 “올바르지 않은 목적·운용 적합성”을 별도 문제로 다루지 않습니다. “usefulness”는 intended use와 operational environment의 의미를 지나치게 약화할 수 있습니다.

- **`:42-44` — 산출물과 책임이 추상적.**  
  traceability와 baseline은 언급하지만 stakeholder expectation, requirement, verification result, validation evidence 사이의 구체적인 추적 관계가 없습니다.

- **`:46` — LLM 변형이 충분하지 않음.**  
  deterministic check와 requirement-based test를 verification으로, scenario와 usefulness를 validation으로 배치하지만, 누가 intended environment를 대표하는지, 비결정적 실행을 어떻게 재현·판정하는지, 독립성은 어떻게 확보하는지 빠졌습니다.

- **`:48` — NASA 모델을 순차 생명주기로 묘사할 위험.**  
  “one large sequential lifecycle”을 미채택했다고 하지만 NASA 시스템공학은 반복적·재귀적 적용을 포함합니다. 실제 미채택 사항과 모델에 원래 없던 특성을 구분해야 합니다.

### 위험 주도 반복

- **`historical-foundations.md:52-58` — 위험을 선택 기준으로 삼는다는 요지만 있음.**  
  Spiral model의 목표·대안·제약 식별, 위험 해소, 이해관계자 평가, 다음 주기 계획이 빠졌습니다. P0–P5와 bounded research를 왜 spiral 계승으로 보는지도 추적할 수 없습니다.

- **`:60` — 원전을 잘못 대비할 가능성.**  
  Spiral model 자체도 무제한 반복을 뜻하지 않습니다. owner, stop condition, resource limit은 미채택의 근거라기보다 기존 위험 관리 원칙을 하네스에 구체화한 것으로 보는 편이 자연스럽습니다.

### Agile·TDD·CI

- **`historical-foundations.md:64-72` — 세 개의 별도 전통을 한 모델처럼 처리.**  
  하나의 original problem, retained principle, adaptation, not-adopted 문단으로 Agile, TDD, CI를 모두 설명합니다. 모델별 완결성 요구를 충족하지 못합니다.

- **`:66-68` — TDD와 CI의 고유 문제를 잃음.**  
  TDD의 명세 예제화·설계 피드백·회귀 보호와 CI의 장기 분기·통합 지옥·빠른 공동 피드백이 “large batches”라는 일반론으로 축소됐습니다.

- **`:70` — TDD를 독립 QA와 혼동할 여지.**  
  “independent expected results are not writable by the implementer”는 개발자가 테스트를 작성하는 TDD와 독립 acceptance test를 구분하지 않습니다. 구현자 작성 단위 테스트와 독립 품질 판정을 별도로 설명해야 합니다.

- **`:70-72` — CI의 LLM 변형과 미채택 사항이 없음.**  
  mainline integration, 자동 빌드, 빠른 실패 복구, 생성된 테스트의 자기확증 위험, 비결정적 검사 처리 등이 없습니다. 미채택 문단도 Agile의 변경 대응만 다룹니다.

- **`historical-foundations.md:161-163` — 역사적 원전 품질 불균형.**  
  CI는 Fowler의 해설, TDD는 Agile Alliance 용어집만 인용합니다. 역사적 계보를 주장하려면 초기·대표 원전 또는 이를 대신하는 이유가 필요합니다.

### 구성 기준선과 event history

- **`historical-foundations.md:76-84` — Event Sourcing과 감사 로그의 경계가 불명확.**  
  Event Sourcing은 이벤트로부터 권위 있는 상태를 재구성하는 모델인데, 하네스 설명은 append-only audit history일 수도 있습니다. 실제로 이벤트 fold/replay가 권위 상태를 생성하는지 밝혀야 합니다.

- **`:80-82` — 핵심 동작 누락.**  
  이벤트 불변성, 순서 범위, 명령과 이벤트 구분, 결정적 재생, 이벤트 스키마 진화, 중복 적용 방지가 없습니다. 이 상태에서 Event Sourcing의 계승을 주장하면 과장될 수 있습니다.

- **`:84` — 좋은 한계지만 미채택 관행은 아님.**  
  외부 서비스의 진실을 증명하지 못한다는 점은 중요한 증거 한계입니다. 다만 Event Sourcing에서 의도적으로 채택하지 않은 요소를 설명하지는 않습니다.

### 생명주기 보안

- **`historical-foundations.md:88-92` — SDL과 SSDF를 일반 원칙으로만 요약.**  
  위협 모델링, 보안 요구사항, 안전한 설계·구현, 취약점 관리, 대응 준비 등 실제 lifecycle practice와 하네스 통제의 대응 관계가 없습니다.

- **`:94` — LLM 환경 변화가 구체적이지 않음.**  
  prompt injection, 도구 권한 남용, 비밀 유출, 모델·공급자 경계, 비신뢰 입력 같은 LLM 고유 위협 대신 “security perspective always exists”만 제시합니다. 다른 품질 속성으로의 확장은 출처 계승이 아니라 하네스의 일반화인데 이를 명시하지 않습니다.

- **`:96` — 적합성 부인과 미채택을 혼동.**  
  SDL/SSDF 적합성을 주장하지 않는다는 단서는 좋습니다. 그러나 어떤 practice를 범위·비용·위험 때문에 의도적으로 제외했는지는 여전히 없습니다.

### 공급망 provenance

- **`historical-foundations.md:100-104` — 원칙을 절대화.**  
  “every transformation”과 “authorized producer”는 in-toto식 사고와 맞지만, 실제 provenance 완전성은 선택한 수준·범위·검증 정책에 좌우됩니다. 적용 범위를 특정해야 합니다.

- **`:106-115` — 하네스 확장 사슬은 명확하지만 계승 근거가 약함.**  
  mission부터 release까지의 사슬은 좋은 개념도입니다. 그러나 material, subject digest, attestation, signer/builder identity, verification policy와 어떻게 대응하는지 없어 공급망 provenance를 실제 채택한 것인지 넓은 비유인지 판단하기 어렵습니다. LLM 모델·프롬프트·검색 입력·도구 버전도 명시적으로 드러나지 않습니다.

- **`:117` — 유사성 구분을 한 유일한 문단.**  
  “similar provenance reasoning”이라고 하여 in-toto/SLSA 적합성과 유사성을 구분한 점은 좋습니다. 다만 이는 오히려 문서 앞부분의 “shaped/lineage” 주장과 긴장 관계에 있습니다.

### Durable execution

- **`historical-foundations.md:121` — 현대 제품 문서이지 역사적 계보는 아님.**  
  Temporal, DBOS, Dapr는 유용한 reference implementation이지만, 이전의 workflow recovery, checkpoint/restart, transaction, saga 계보는 없습니다.

- **`:125` — 여러 보장 수준을 한 원칙으로 합침.**  
  workflow replay, workflow/task/activity retry, duplicate suppression, operation ID, reconciliation, compensation은 서로 다른 범위의 기법입니다. 어떤 출처가 어느 원칙을 뒷받침하는지 알 수 없습니다.

- **`:127` — 결정적 replay와 LLM 비결정성의 충돌 누락.**  
  Temporal식 replay에서는 모델 호출과 외부 효과를 orchestration replay 내부에서 다시 실행하지 않아야 합니다. 모델·도구 호출을 기록된 activity 결과로 다루는지 등의 핵심 LLM 변형이 없습니다.

- **`:129` — exactly-once 부인은 적절함.**  
  응답 유실 뒤 효과가 이미 성공했을 수 있다는 설명은 강점입니다. 다만 workflow, 결과 commit, 외부 side effect별 보장 범위를 더 나눠야 합니다.

### 증거 중심 완료 판정

- **`historical-foundations.md:131-145` — 요구된 역사적 모델이 사실상 누락.**  
  LLM 실패 유형과 하네스 해법만 있고 original problem, inherited principle, adaptation, not-adopted, 역사적 출처가 없습니다.

- **`:139-143` — 증거의 충분성 규칙이 없음.**  
  checked artifact와 evidence를 말하지만 진정성, 최신성, 후보 귀속, 요구사항 관련성, 독립성, 부정적 증거, 불확실성, 면제·잔여 위험을 누가 어떻게 판단하는지 없습니다.

- **`:142` — 독립성 주장도 정의가 부족함.**  
  authority, workspace, method, model provenance는 필요한 단서일 수 있지만, 같은 모델 계열·학습 자료·공유 문맥에서 오는 상관 오류를 얼마나 줄였는지 측정 기준이 없습니다.

- **`:145` — 독창성 과장 가능성이 큼.**  
  “main architectural step beyond the historical reference models”는 assurance case, 독립 V&V, 정책 집행, capability security 등과의 비교 없이 제시된 독창성 주장입니다. “이 하네스가 이 모델들을 종합한 방식” 정도로 제한해야 입증 가능합니다.

### 개요 문서와 근거 원장

- **`docs/architecture.md:43-62` — 요약도 모델을 병합함.**  
  event history와 구성 관리, secure lifecycle과 공급망 provenance, Agile·TDD·CI를 각각 한 행으로 묶습니다. `:62`의 “각 tradition별 네 항목을 설명한다”는 안내는 상세 문서의 실제 내용보다 강합니다.

- **`architecture.md:31-39, 88-99` — 완료 판정은 목표 규칙으로만 존재.**  
  quality decision과 evidence-based completion을 정의하지만 역사적 출처나 계승 관계는 없습니다.

- **`architecture.md:5, 80-86` — 강점.**  
  목표 아키텍처와 현재 구현 상태를 명확히 분리하여 역사적 원칙을 구현 완료 주장으로 오해할 위험을 낮춥니다.

- **`evidence/historical-foundations-ledger.json:1-20` — 인용 목록일 뿐 evidence ledger로는 부족.**  
  저자, 발표 연도, 판본, 출처 유형, 보존 사본·해시, 인용 페이지·절, 지원하는 claim ID, 직접 영향/사후 적용/단순 유사성 분류가 없습니다. 변경 가능한 웹 문서도 버전 고정 없이 URL과 접근일만 기록했습니다.

## 결론

- **가장 큰 누락:** 증거 중심 완료 판정의 역사적 reference model.
- **가장 큰 구조 문제:** V&V, TDD, CI 등 별도 모델을 묶어 모델별 네 질문에 답하지 않음.
