# LLM 작업의 허위 완료·중단·재시도를 줄이는 실행 설계

## 1. 조사 질문

LLM 작업자가 실제 작업을 하지 않았는데도 완료했다고 보고하거나, 실행 도중 정지·오류·중단되어 전체 작업을 다시 해야 하거나, 검증 LLM이 잘못된 판정을 내리는 문제를 다른 워크플로 시스템과 LLM 에이전트 프레임워크는 어떻게 다루는가?

이 문서는 다음 사용자 기준을 구체적인 실행 규칙으로 바꾸기 위한 조사 기록이다.

> 완료된 작업은 정상적인 독립 재확인에서 다시 수행할 필요가 없어야 한다. 결과가 틀렸거나 허위였거나 의도하지 않게 중단되어 다시 해야 한다면 완료가 아니다.

## 2. 조사 결론

다른 시스템도 LLM의 `done` 문장을 완료 근거로 삼지 않는다. 안정적인 방식은 다음 다섯 요소를 결합한다.

1. 작업 진행 상태를 외부 저장소에 단계별로 기록한다.
2. 성공한 단계는 다시 실행하지 않고 실패한 최소 단위에서 이어 간다.
3. 외부 효과가 있는 작업은 중복 실행해도 결과가 하나만 생기도록 중복 제거 키를 사용한다.
4. 일시적 오류와 영구 오류를 나눠 재시도 여부와 대체 경로를 결정한다.
5. LLM 평가는 보조 판단으로 사용하고, 파일·프로세스·해시·시험 결과처럼 결정론적으로 확인할 수 있는 사실을 우선한다.

Temporal은 사건 이력으로 실행 상태와 진행을 보존해 장애 뒤 마지막 기록 지점부터 이어 가는 내구성 있는 실행을 제공한다.[1] AWS Step Functions의 redrive도 성공한 단계의 결과와 이력을 보존하고 실패한 단계부터 같은 입력으로 다시 실행한다.[18] LangGraph는 단계별 체크포인트와 개별 작업 쓰기를 보존해 병렬 단계 중 성공한 노드를 재실행하지 않고 실패한 부분부터 재개할 수 있다고 설명한다.[6]

따라서 사용자의 기준은 다음처럼 엄밀하게 표현할 수 있다.

> **완료 전**에는 일시적 오류에 대한 제한된 재시도와 중단 지점부터의 재개를 허용한다. **완료 후** 정상적인 독립 재확인에서 결과를 다시 만들거나 고쳐야 한다면 기존 완료 사건을 잘못된 판정으로 처리한다.

## 3. 왜 단일 `완료` 응답을 믿으면 안 되는가

OpenAI Agents SDK의 기본 실행 루프에서 최종 출력은 원하는 자료형의 텍스트가 나오고 남은 도구 호출이 없으면 성립한다.[9] 이는 대화 실행이 끝났다는 뜻이지, 실제 요구를 충족했다는 뜻은 아니다. 출력 방어 규칙도 최종 출력을 검사할 수 있지만, SDK 문서상 에이전트 수준의 입력·출력 방어 규칙은 각각 첫 에이전트와 최종 에이전트 경계에만 적용되며 모든 도구·인계 경로를 자동으로 포괄하지 않는다.[8]

따라서 하네스에서는 다음 값들을 분리해야 한다.

- `에이전트 실행 종료`: LLM 호출이 더 이상 진행되지 않음
- `작업 시도 종료`: 한 번의 작업 시도가 성공·실패·시간 초과·중단으로 끝남
- `산출물 제출`: 파일이나 실행 기록이 제출됨
- `검증 통과`: 요구된 검사가 산출물을 실제로 확인함
- `단계 완료`: 필수 작업과 검증이 모두 충족됨
- `미션 완료`: 모든 필수 단계와 출시 판정이 충족됨

LLM은 작업 시도의 결과와 산출물을 제출할 수 있지만, 자기 응답만으로 단계나 미션을 완료 상태로 바꿀 수 없어야 한다.

실행 관찰도 별도 근거로 남겨야 한다. OpenAI Agents SDK의 추적 기능은 모델 생성, 도구 호출, 역할 인계, 방어 규칙 실행을 한 실행 흐름의 span으로 기록한다.[10] 다만 추적 기록은 무엇이 실행됐는지를 보여 줄 뿐, 요구를 충족했다는 판정을 자동으로 대신하지는 않는다.

## 4. 일반 시스템이 쓰는 복구 방식

### 4.1 사건 이력과 체크포인트

Temporal은 각 실행 단계의 사건 이력으로 상태를 복원한다.[1] LangGraph 체크포인터는 각 상위 단계와 개별 노드 쓰기를 저장하고, 중단 뒤 같은 작업 흐름 식별자로 이어 간다.[6] AWS Step Functions는 성공한 단계의 이력을 유지하면서 실패·중단·시간 초과 단계부터 redrive한다.[18]

LangGraph는 단일 실행을 넘겨 상태를 유지하는 체크포인터와 여러 실행에서 공유할 자료 저장소를 구분한다.[4] 또한 외부 판단이 필요한 지점에서 실행 상태를 저장한 뒤 일시 정지하고, 같은 작업 흐름 식별자로 이어서 실행하는 중단 기능을 제공한다.[7]

하네스 적용안은 다음과 같다.

- 하나의 논리 작업에는 재시도 중에도 바뀌지 않는 `invocation_id`를 부여하고, 실제 시도마다 새 `attempt_id`를 부여한다.
- 시작·진행·산출물 기록·중단·실패·성공을 append-only 사건으로 남긴다.
- 체크포인트에는 입력 해시, 현재 후보본, 완료한 하위 작업, 생성된 산출물 해시, 다음 실행 위치를 기록한다.
- 재개 시 이전 성공 산출물의 해시와 계보를 다시 확인한다.
- 재검산에 실패한 성공 기록은 재사용하지 않고 `STALE`로 바꾼다.

### 4.2 전체 작업이 아니라 실패한 최소 단위 재시도

Temporal은 실패 가능하거나 비결정적인 API·LLM 호출을 별도 Activity로 두고 그 Activity에 재시도 정책을 적용할 것을 권한다.[2] 전체 Workflow를 무작정 다시 실행하면 같은 결정론적 논리를 반복해 비용만 늘리고 근본 원인을 해결하지 못할 수 있다고 설명한다.[2]

하네스에서도 한 전문가의 업무를 너무 큰 단위로 묶지 않는다.

- 조사: 출처 발견 → 원문 확보 → 주장 추출 → 적용 가능성 평가
- 구현: 시험 작성 → 코드 변경 → 부분 시험 → 후보본 동결
- 검증: 자료 검산 → 명령 실행 → 결과 판정 → 지적 등록

각 하위 작업이 별도 체크포인트와 산출물을 가지면 마지막 실패 지점만 다시 수행할 수 있다.

### 4.3 중복 실행에 안전한 외부 효과

Temporal Activity는 적어도 한 번 실행될 수 있으므로 멱등성을 강하게 권고한다. 작업자가 성공 뒤 보고 전에 정지하면 같은 Activity가 다시 실행될 수 있기 때문이다.[3] 공식 문서는 실행 ID와 Activity ID를 결합한 중복 제거 키를 외부 서비스에 전달하는 예를 제시한다.[3]

워크플로 실행 자체의 중복과 외부 부작용의 중복은 별도로 막아야 한다. Temporal은 같은 Workflow ID의 완료 실행을 다시 시작하지 않는 정책을 제공하지만, 이 정책의 확인 범위는 보존 기간 안의 실행에 한정된다.[19] 외부 Activity는 기본적으로 적어도 한 번 실행될 수 있으므로 Workflow ID만으로 파일 게시·결제·알림 같은 부작용의 중복을 막을 수 없다.[20]

하네스에서는 다음 식별자를 외부 효과 키로 사용한다.

```text
mission_id + revision + task_id + invocation_id + operation_id
```

여기서 `invocation_id`는 같은 논리 작업의 모든 시도에서 유지된다. 시도마다 달라지는 `attempt_id`를 이 키에 넣으면 재시도가 새 외부 효과를 만들 수 있으므로 넣지 않는다. 같은 키의 파일 게시·이슈 생성·패키지 배포·알림 발송 요청이 다시 오면 새 효과를 만들지 않고 기존 결과 영수증을 반환해야 한다. 외부 시스템이 중복 제거를 지원하지 않으면 실행 전후 상태를 조회해 결과를 대조하고, 결과가 불명확하면 자동 재시도하지 않는다.

앞 단계의 외부 효과는 성공했지만 뒤 단계가 영구 실패한 경우에는 재시도만으로 일관성을 되찾을 수 없다. 이때는 예약 취소·임시 자원 삭제·발행 철회처럼 도메인에 맞는 보상 동작을 실행하거나, 되돌릴 수 없는 효과의 현재 상태를 대조해 제한된 결과로 판정한다. 보상은 데이터베이스 전체를 과거 시점으로 되돌리는 동작이 아니라 앞서 수행한 효과를 의미상 상쇄하는 별도 작업이며, 보상 자체도 중복 실행에 안전해야 한다.[21]

### 4.4 오류 종류에 따른 재시도와 대체 경로

Temporal은 일시적 오류, 간헐적 오류, 영구 오류를 구분하고 영구 오류에는 재시도를 적용하지 말 것을 안내한다.[3] LangGraph도 오류 종류·시도 횟수·지수형 대기·시간 제한을 설정하고, 반복 실패 시 다른 API 같은 대체 경로로 전환하는 예를 제공한다.[5] AWS Step Functions 역시 오류 이름별 재시도, 최대 횟수, 대기 증가율과 최대 대기 시간을 명시한다.[17]

하네스의 기본 분류는 다음과 같다.

| 실패 종류 | 처리 |
|---|---|
| 짧은 네트워크 단절·일시적 서비스 오류 | 같은 하위 작업을 제한 횟수만 자동 재시도 |
| 사용량 제한·혼잡 | 지수형 대기와 무작위 지연 뒤 재시도 |
| 응답 형식 오류 | 한 번의 구조 복구 시도 뒤 다른 모델 또는 결정론적 파서 사용 |
| 진전 없는 장시간 실행 | 중단하고 마지막 유효 체크포인트에서 다른 실행기로 재개 |
| 잘못된 입력·모순된 요구 | 재시도하지 않고 요구·목적 책임 축으로 반환 |
| 같은 추론 오류 반복 | 같은 프롬프트 재실행을 중단하고 조사 또는 다른 전문 경로 사용 |
| 외부 효과 성공 여부 불명 | 상태 대조 전까지 재시도 금지 |
| 앞 단계 외부 효과 성공 뒤 후속 단계 영구 실패 | 등록된 보상 동작 또는 상태 대조를 수행하고 보상 결과를 별도 증거로 기록 |
| 정책·권한 위반 | 즉시 실패하고 같은 권한으로 재시도 금지 |
| 검증자 간 판정 불일치 | 근거 대조, 순서 교환 평가, 독립 검증 또는 조사 단계로 전환 |

재시도에는 횟수·시간·토큰 한도가 있어야 한다. 한도를 넘기면 무한 반복하지 않고 `BLOCKED`, `RESEARCH_NEEDED`, `FAILED` 중 하나로 전이한다.

### 4.5 진행 신호와 시간 초과

LangGraph는 한 번의 실행에 대한 전체 시간 제한과 진전이 없을 때의 유휴 시간 제한을 구분한다. 명시적 heartbeat만 유휴 시간을 갱신하도록 설정할 수도 있다.[5]

LLM이 단순히 “작업 중”이라고 말하는 것을 진전으로 인정하면 안 된다. 하네스의 진행 신호에는 다음 중 하나가 새로 있어야 한다.

- 새 사건 번호
- 새 체크포인트 해시
- 새 산출물 또는 산출물 변경 해시
- 완료된 하위 작업 ID
- 도구 실행 영수증
- 검산 가능한 조사 출처 추가

새 근거가 없는 반복 메시지는 heartbeat로 인정하지 않는다.

계획된 배포·작업자 교체·서비스 종료에서는 실행을 즉시 끊지 않고 현재의 안전한 상위 단계 경계까지 마친 뒤 체크포인트를 저장하는 정상 종료 절차를 사용한다. 갑작스러운 장애에는 이 절차가 적용되지 않으므로 시간 제한·heartbeat·중복 억제를 함께 유지해야 한다. LangGraph도 현재 superstep 뒤에 종료하고 재개 가능한 체크포인트를 남기는 협력적 종료 방식을 설명한다.[5]

### 4.6 주요 에이전트 프레임워크 비교에서 얻은 한계

Google ADK는 완료된 이벤트와 작업 결과를 복원해 순차·반복·병렬 흐름을 이어 갈 수 있지만, 도구가 적어도 한 번 실행되며 재개 중 두 번 이상 실행될 수 있음을 명시한다. 사용자 정의 에이전트는 보존할 단계와 상태를 직접 정의해야 하며, 멈춘 흐름의 구성을 바꾼 뒤 재개하는 방식은 지원하지 않는다.[22]

CrewAI는 작업 진행·중간 출력·기억·사건 이력을 체크포인트에 보존하고 완료 작업을 건너뛸 수 있다. 그러나 사건에 따라 자동으로 쓰는 체크포인트는 저장 실패를 기록만 하고 실행을 계속하는 최선 노력 방식이다. 따라서 완료 경계처럼 잃어서는 안 되는 시점에는 저장 실패를 호출자에게 돌려주는 명시적 체크포인트를 사용하고, 저장 성공을 확인하기 전에는 단계를 완료하지 않아야 한다.[23]

Microsoft Agent Framework Workflows는 상위 단계 끝에서 실행기 상태·대기 메시지·요청과 응답·공유 상태를 저장하고 새 실행에서 복원할 수 있다. 복원할 때는 원래 흐름의 구성과 실행기 식별자를 유지해야 한다.[24]

이 비교가 보여 주는 공통점은 프레임워크의 `final`, 마지막 메서드 반환, 반복 횟수 소진, 실행기 종료가 업무 품질의 완료를 보장하지 않는다는 점이다. 체크포인트 기능이 있어도 외부 부작용 중복 억제, 완료 품질 기준, 독립 검증, 복원 호환성은 하네스 정책으로 별도 강제해야 한다.

## 5. 검증 LLM도 틀릴 수 있다는 연구 결과

LLM 심판은 확장성이 있지만 절대적인 심판은 아니다. MT-Bench 연구는 강한 LLM 심판이 사람 선호와 80% 이상 일치할 수 있다고 보고하면서도 위치·장황함·자기선호 편향과 제한된 추론 능력을 확인했다.[13] 별도 연구에서는 후보 답변의 제시 순서만 바꿔도 평가 결과가 크게 변할 수 있음을 보였고, 여러 평가 근거 생성, 제시 순서 균형화, 불확실한 사례의 사람 검토를 제안했다.[12]

CriticGPT 연구에서는 LLM 비평이 사람의 버그 발견을 도울 수 있었지만, 존재하지 않는 버그를 지어내 사람의 판단을 오도할 수 있다는 한계도 확인됐다.[15] 과정 감독 연구는 최종 답만 평가하는 방식보다 중간 추론 단계에 피드백을 주는 방식이 해당 수학 과제에서 더 좋은 결과를 보였지만, 이는 모든 프로그래밍 과업에서 자동으로 같은 효과를 보장하지는 않는다.[14]

따라서 “검증 LLM을 한 번 더 호출”하는 것만으로 신뢰 문제가 해결되지 않는다.

## 6. 검증자를 검증하는 다층 구조

### 6.1 1층: 결정론적 사실 검사

가능한 사실은 LLM에게 판정시키지 않는다.

- 파일 존재와 크기
- SHA-256
- JSON Schema
- 미션·revision·후보본 ID 일치
- 실행 명령과 종료 코드
- 시험 결과 원문
- 허용 경로 밖 쓰기
- Git diff와 빌드 내용
- 출처 URL 접근 여부와 인용문 존재 여부

이 층이 실패하면 LLM 검토 의견과 무관하게 통과시키지 않는다.

### 6.2 2층: 분야별 의미 검증

결정론적 검사로 판단할 수 없는 의미를 세부 검증 전문가에게 나눈다.

- 요구 의미와 구현 의미 일치
- 보안 위협과 우회 가능성
- 알고리즘·통계 방법 적합성
- 사용자 목적에 대한 적합성
- 남은 위험과 적용 범위

여러 검증자를 단순히 같은 질문으로 복제하지 않는다. 서로 다른 판단 축과 독립 자료를 배정한다. Anthropic도 복잡한 평가에서 고려 사항을 분리하거나 여러 관점으로 병렬 평가하고, 명확한 평가 기준이 있을 때 평가자-개선자 반복을 쓰는 방식을 설명한다.[16]

### 6.3 3층: 판정 대조와 이견 처리

- 후보를 바로 둘씩 비교하기 전에 각 후보를 품질 항목별로 독립 평가한다. 직접 비교는 장황함·권위적인 문체 같은 표면적 특성의 영향을 더 크게 받을 수 있으며, 독립 평가를 먼저 수행한 뒤 비교하는 방식이 이를 줄인 연구가 있다.[25]
- 비교할 때는 `(A, B)`와 `(B, A)` 순서를 모두 사용한다. 순서를 바꿨을 때 판정이 뒤집히면 자동 통과시키지 않는다.
- 각 지적은 후보본 위치와 재현 절차를 가리켜야 한다.
- 재현되지 않는 지적은 자동으로 사실로 채택하지 않는다.
- 통과 판정도 필수 증거 전체와 연결돼야 한다.
- 복수 검증이 필요하면 같은 모델에 역할 이름만 바꾸기보다 가능한 범위에서 서로 다른 모델 계열을 사용하고, 첫 판정 전에는 다른 검증자의 결론을 보여 주지 않는다. 서로 다른 모델 계열의 패널이 연구된 평가 설정에서 단일 대형 심판보다 좋은 결과와 낮은 동일 모델 편향을 보였지만, 패널 합의가 외부 오라클을 대신하지는 않는다.[26]
- 검증자 간 이견이 크면 같은 모델의 다수결보다 외부 근거 조사나 별도 오라클을 우선한다. 객관적 지식·논리·수학·코딩의 어려운 비교에서는 강한 LLM 심판도 무작위 추측에 가까운 결과를 낸 평가가 있으므로, 주관적 선호 일치율을 정답 판별 능력으로 일반화하지 않는다.[28]
- 판정 신뢰도가 낮거나 순서 교환에서 결과가 뒤집히거나 분포 밖 사례이면 자동 통과 범위를 줄이고 더 강한 검증자·전문가·사용자 결정으로 상향한다. 이 방식의 통계적 보증은 보정 자료와 실제 평가 자료가 같은 분포라는 전제에 의존한다.[27]
- 공개된 해결책이 부족하면 연구·기술개발 과업으로 전환한다.
- 목표·큰 비용·보안·외부 효과를 바꾸는 결정만 사용자에게 권고안과 함께 올린다.

민감한 도구 실행은 검증 LLM의 자유 재량으로 바로 실행하지 않는다. OpenAI Agents SDK의 사람 개입 흐름처럼 특정 도구 호출을 일시 정지하고, 호출별 승인 여부와 정지 상태를 저장한 뒤 원래 실행을 재개하는 방식이 참고가 된다.[11]

### 6.4 사용자와 합의한 품질 보증 판정

검증자의 역할은 결함 수를 세거나 무결점을 요구하는 것이 아니다. 결과물이 사용자가 원하는 결과에 도달하는 데 충분히 기여하며 합의된 품질 수준을 충족하는지 보증하는 것이다. 재현된 결함은 판정 근거이지만 그 자체가 자동 실패를 뜻하지 않는다.

품질 판정은 두 층으로 구성한다.

1. 정확성·보안·자료 무결성·필수 기능과 과업별 핵심 품질에는 각각 최소 하한을 둔다. 이 항목들은 서로 상쇄하지 않으며 하나라도 하한에 미달하면 실패다.
2. 모든 필수 하한을 충족한 뒤 사용성·유지보수성·성능 여유·문서성·운영 편의성 같은 개선 품질을 원하는 결과에 대한 기여도로 종합 평가한다.

각 결함 기록은 영향을 받는 품질 항목, 관찰값, 최소 하한, 결과 달성에 미치는 영향, 재현 근거를 포함해야 한다. 결함이 있어도 모든 필수 품질이 하한 이상이고 전체 결과에 대한 기여가 충분하면 통과할 수 있다. 일부 범위에서만 기준을 충족하면 제한적 출시를 검토하며, 근거가 부족해 품질을 판정할 수 없으면 통과가 아니라 판정 보류로 처리한다.

## 7. 세 책임 축에 적용하는 방식

### 7.1 요구·목적 책임 축

- 완료 판정 기준을 구현 전에 작성한다.
- 정상·경계·오류·중단·재개 시나리오를 포함한다.
- 어떤 산출물과 검사가 있어야 재작업 없이 수락할 수 있는지 정한다.
- 프로그래밍·검증 전문가의 기술 의견을 요구에 반영한다.

### 7.2 프로그래밍·해결 책임 축

- 작업을 체크포인트 가능한 최소 단위로 나눈다.
- 외부 효과에 중복 제거 키와 상태 대조 절차를 둔다.
- 실패 종류와 대체 경로를 구현한다.
- 자기 구현의 최종 통과를 판정하지 않는다.

### 7.3 검증·판단 책임 축

- 요구 단계부터 독립 기대값과 반례를 마련한다.
- 결정론적 사실 검사를 먼저 실행한다.
- 의미 판단에는 분야별 검증자를 동적으로 구성한다.
- 지적과 통과 판정 모두 실제 위치·명령·산출물·해시에 연결한다.
- 검증자 자신의 불확실성과 판정 이견을 숨기지 않는다.

### 7.4 사용자와 합의한 동적 품질 프로필

품질 하한과 개선 목표는 요구·목적, 프로그래밍·해결, 검증·판단의 세 책임 축이 요구 작성 단계에서 공동으로 만든다. 요구·목적 책임 축은 사용 목적과 필요한 결과를, 프로그래밍·해결 책임 축은 구현 가능성·비용·기술 제약을, 검증·판단 책임 축은 측정 가능성·오라클·반례·필요 증거를 제시한다. 총괄 관리자는 품질 프로필이 목표와 동떨어지거나 지나치게 낮거나 과도하지 않은지 확인한 뒤 기준선을 확정하며, 내용을 단독으로 다시 작성하지 않는다.

품질 프로필은 고정 점수표가 아니라 미션의 목적과 위험에서 동적으로 생성한다. 다음 유형은 출발점일 뿐 최종 목록을 고정하지 않는다.

- 시제품은 지정된 최적 조건에서 핵심 동작을 빠르게 입증하고 적용 한계를 명시하는 데 초점을 둔다.
- 일반 프로그램은 정상·경계·일반 오류를 적절히 처리하고 안정성·유지보수성을 확보한다.
- 보안 프로그램은 악의적인 입력과 권한 우회에 강건해야 하며 기본 거부와 부정 시험을 요구한다.
- 논문용 프로그램은 과학적으로 검증 가능하고 타당한 방법을 사용하며 방법 타당성·의미 일치·평가지표 검산·실험 무결성·재현 계보를 별도로 확인한다.

각 품질 항목은 식별자, 원하는 결과에 대한 기여, 필수 하한 또는 개선 목표 구분, 측정 방법, 기준값, 필수 증거, 미달 영향, 적용 범위, 다시 검토할 변경 조건을 가진다. 기준선 확정 뒤 한 책임 축이 단독으로 값을 낮추거나 높일 수 없다. 변경은 새 revision과 영향받은 증거의 `STALE` 처리를 거치며, 사용자 목표나 위험 수용 수준을 바꾸는 경우에만 정리된 권고안과 함께 사용자에게 요청한다.

## 8. 제안하는 작업 상태

```text
PLANNED
  → RUNNING
  → WAITING_EXTERNAL      외부 응답 대기
  → RETRY_SCHEDULED       일시적 오류, 완료 전 제한 재시도
  → RECOVERING            마지막 체크포인트에서 재개
  → OUTPUT_SUBMITTED      산출물 제출, 아직 완료 아님
  → VERIFYING
  → VERIFIED
  → COMPLETED
```

실패 계열은 다음처럼 구분한다.

```text
BLOCKED                 필요한 입력이나 권한 부족
RESEARCH_NEEDED         공개된 방법이나 현재 근거 부족
FAILED_RETRYABLE        정책 범위 안에서 재시도 가능
FAILED_PERMANENT        같은 입력·방법으로 재시도해도 해결되지 않음
STALE                   입력·요구·후보본 변경으로 기존 결과 무효
CANCELLED               명시적으로 중단
```

`COMPLETED`는 LLM이 직접 제출할 수 있는 상태가 아니다. 정책 엔진이 다음 조건을 모두 확인한 뒤에만 전이한다.

1. 필수 하위 작업이 모두 `VERIFIED`다.
2. 요구된 산출물이 존재하고 해시가 일치한다.
3. 실행형 작업은 명령·환경·종료 코드·원시 출력이 있다.
4. 판단형 작업은 출처·인용·비교 기준·적용 판단이 있다.
5. 미해결 차단 지적과 보상 대기 작업이 없다.
6. 검증 역할이 작업 수행 역할과 분리돼 있다.
7. 현재 미션·revision·후보본과 모든 근거가 일치한다.
8. 같은 입력과 후보본을 독립적으로 재확인해도 재작업 요구가 발생하지 않는다.

## 9. 사용자와 합의한 완료 기준

하네스에 넣을 핵심 불변 조건을 다음과 같이 확정했다.

> **완료 안정성:** 완료로 판정된 작업은 같은 입력·요구 기준선·후보본을 대상으로 한 정상적인 독립 재확인에서 다시 수행하거나 수정할 필요가 없어야 한다. 재작업이 필요하다고 확인되면 기존 완료 판정은 무효이며, 원인을 허위 보고·잘못된 판정·증거 누락·중단 복구 실패 중 하나로 기록한다.

> **복구 가능성:** 완료 전에 발생한 일시적 오류·정지·프로세스 중단은 이미 검증된 작업을 반복하지 않고 마지막 유효 체크포인트에서 재개한다.

> **중복 안전성:** 재개 과정에서 같은 외부 효과가 다시 요청되더라도 중복 제거 키·상태 대조·보상 절차로 결과가 중복되지 않아야 한다.

> **검증자 불신 원칙:** LLM 검증자의 통과·실패 문장은 단독 증거가 아니다. 결정론적 사실, 재현 가능한 지적, 독립 자료와 이견 대조를 통해 판정을 구성한다.

자동 재시도와 체크포인트 재개는 `COMPLETED` 이전 상태에서만 수행한다. `COMPLETED` 뒤 독립 재확인에서 재작업이 필요하다고 확인되면 기존 완료 사건을 무효화하고, 새 시도 번호와 원인 분류를 가진 복구 작업을 만든다. 기존 완료 기록을 지우지 않고 잘못된 판정이었다는 후속 사건을 추가한다.

## 10. 현재 하네스에 권하는 구현 순서

1. 작업 시도·체크포인트·진행 사건 모델
2. 오류 분류와 재시도 한도
3. 성공한 하위 작업 재사용과 `STALE` 전파
4. 외부 효과 중복 제거 키와 결과 대조
5. 산출물 제출과 완료 판정 분리
6. 결정론적 사실 검사 실행기
7. 분야별 검증 전문가와 이견 처리
8. 허위 완료·중단·중복 효과·검증자 오류 결함 주입 시험
9. 조사·기술개발 전환과 자원 임계값 적용
10. 결과를 기술 글과 사건 원장에 연결

이 순서에서는 LLM의 지시 준수를 권한 경계로 사용하지 않는다. 완료·재개·재시도·무효화는 결정론적 상태 기계와 실제 산출물 검사로 집행한다.
