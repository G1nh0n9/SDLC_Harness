# 0001. 세 책임 축과 총괄 관리자

- 상태: `accepted`

## 맥락

기존 역할 명단은 단계마다 전문가 이름을 만들 수 있지만, 요구 작성·프로그래밍·검증이 요구 단계부터 함께 품질을 설계하는 상위 책임 구조가 분명하지 않았다. 관리자가 구현·검토·승인까지 겸하면 자기 작업을 자기가 통과시키는 문제가 생긴다.

## 결정

모든 미션에 다음 세 책임 축을 둔다.

1. 요구·목적
2. 프로그래밍·해결
3. 검증·품질 보증

세 책임 축은 목표·요구·품질 하한·검증 방법을 공동 작성한다. 구현과 최종 품질 판정은 서로 다른 권한과 작업 공간에서 수행한다.

총괄 관리자는 네 번째 전문 부서가 아니라 계획·권한·상태·이견을 조정하는 정책 집행자다. 다음을 겸하지 않는다.

- 구현
- 검증 결과 작성
- 최종 품질 판정
- 자가 승인
- 출시 산출물 내용 작성

## 결과

### 장점

- 요구 단계부터 구현 가능성과 검증 가능성을 함께 반영한다.
- 검증이 마지막 시험 실행에만 머물지 않고 품질 보증이 된다.
- 구현자 자가 승인과 관리자 권한 집중을 차단할 수 있다.
- 회사 부서와 비슷한 책임 구조를 사용자가 이해하기 쉽다.

### 비용

- 세 책임 축의 이견을 정형 기록하고 조정해야 한다.
- 작은 과업에도 최소 책임 구조는 유지해야 한다.
- 역할 문자열이 아니라 실제 권한 증표와 작업 공간 분리가 필요하다.

## 기각한 대안

### 관리자가 전체 결정을 직접 수행

권한 집중과 자기 승인 위험 때문에 기각했다.

### 요구 작성 뒤 프로그래밍, 마지막에 검증

프로그래밍·검증 전문성이 요구 기준에 늦게 반영돼 잘못된 기대값과 시험 불가능한 요구가 생길 수 있어 기각했다.

### 모든 결정을 세 축 만장일치로 처리

해결되지 않은 기술 이견을 사용자에게 떠넘기거나 진행을 멈출 수 있어 기각했다. 이견은 외부 사례 조사와 작은 실험을 먼저 수행한다.

## 확인 방법

- 모든 미션 계획에 세 책임 축이 존재한다.
- 총괄 관리자 권한으로 구현·검증·승인·패키징을 호출하면 거부된다.
- 품질 기준선에는 세 책임 축의 기여가 모두 기록된다.
- 구현 권한으로 최종 품질 판정을 제출하면 거부된다.
