# 실행 요구 기준선 v1

## 1. 목적

사용자 목표와 방법론에서 과업별 개발 단계를 구성하고, 단계별 전문 에이전트를 격리된 권한으로 운용하며, 정형 인계·불변 후보본·검증 가능한 증거에 따라 단계 전이를 통제하는 실행 가능한 하네스를 만든다.

## 2. 범위

### 포함

- 목표 충분성 점검
- 탐색 경로와 제작 경로 분기
- 위험·연구 산출물 여부에 따른 단계와 전문가 동적 구성
- 현재 미션과 사용자 최신 지시 보존
- 다른 미션의 비동기 결과 격리
- 정형 인계 문서 검사
- 후보본 식별·동결·변경 감지
- append-only 증거 원장과 해시 사슬
- 증거 무효화와 단계 통과 정책
- 역할별 도구·경로 권한 프로필
- 작업 공간 materialization
- CLI와 결정론적 종단 시연

### 이번 기준선의 범위 밖

- 임의 운영체제에서 완전한 컨테이너 수준 샌드박스 제공
- 특정 LLM 제공자에 종속된 호출 구현
- 웹 UI와 원격 분산 실행기
- 공식 학회 배지나 보안 인증 자체의 발급

외부 에이전트를 실제 호출하는 부분은 공통 실행 규칙과 Hermes CLI 실행기로 제공하되, 결정론적 시험에서는 기록형 실행기를 사용한다.

## 3. 기능 요구

### 미션과 사용자 지시

- **REQ-MIS-001:** 관리자는 각 과업에 고유한 `mission_id`와 `revision`을 부여한다.
- **REQ-MIS-002:** 현재 미션과 다른 결과는 수신함에 격리하고 현재 상태를 바꾸지 않는다.
- **REQ-MIS-003:** 현재 미션이라도 예상한 단계·작업·후보본과 맞지 않는 결과는 승인 근거로 받지 않는다.
- **REQ-MIS-004:** 사용자의 새 지시는 미션 revision을 올리고 영향받은 계획·작업·증거를 무효화한다.
- **REQ-MIS-005:** 서브에이전트 결과는 자료일 뿐 상태 전이 명령이 아니며 정책 엔진의 판정을 거쳐야 한다.

### 목표 발견과 방법론 계획

- **REQ-GOAL-001:** 목표 정의는 의사결정·결과·대상·분석 단위·시간·제약·질문 유형·자료·결정 기준의 지식 상태를 표현한다.
- **REQ-GOAL-002:** 결론을 바꿀 미확인·충돌 항목이 있으면 목표·방법 탐색 단계를 연다.
- **REQ-GOAL-003:** 충분한 저위험 구현 과업에는 불필요한 탐색 단계를 강제하지 않는다.
- **REQ-PLAN-001:** 계획기는 과업 위험, 질문 유형, 연구 산출물 여부, 미확인 사항에 따라 단계와 역할을 동적으로 구성한다.
- **REQ-PLAN-002:** 연구 산출물에는 방법 타당성·알고리즘 적합성·평가지표 적합성·실험 무결성·결과 재현성과 계보·승인 범위 순수성의 여섯 판정을 모두 넣는다.
- **REQ-PLAN-003:** 여섯 연구 판정은 서로 상쇄할 수 없으며 하나의 필수 판정 실패가 출시를 차단한다.
- **REQ-PLAN-004:** 각 단계는 입력 문서, 출력 문서, 역할, 권한 프로필, 통과 조건, 실패 시 복귀 단계를 선언한다.

### 인계와 역할 격리

- **REQ-HND-001:** 인계 문서는 mission·revision·task·stage·candidate·송수신 역할·산출물 해시·주장·근거·가정·미해결 사항을 포함한다.
- **REQ-HND-002:** 스키마에 맞지 않거나 해시가 맞지 않는 인계는 거부한다.
- **REQ-ROLE-001:** 역할별로 도구, 명령 실행, 읽기·쓰기 경로, 네트워크, 승인 가능 여부를 명시한다.
- **REQ-ROLE-002:** 검토자는 제품 소스와 시험 기대값을 쓸 수 없다.
- **REQ-ROLE-003:** 구현자는 독립 오라클과 승인 기록을 쓸 수 없다.
- **REQ-ROLE-004:** 총괄과 구현자는 자신이 만든 후보본을 최종 승인할 수 없다.
- **REQ-WS-001:** 역할과 작업마다 별도 작업·빌드·임시·홈 디렉터리를 만든다.
- **REQ-WS-002:** 경로 정규화 뒤 허용 루트 밖 절대·상대·심볼릭 링크 경로를 거부한다.

### 후보본과 증거

- **REQ-CAN-001:** 후보본 ID는 소스, 요구·수락 기준선, 설계, 빌드 설정, 의존성, 도구 체인 입력의 결정론적 해시다.
- **REQ-CAN-002:** 동결 뒤 입력이 바뀌면 후보본을 `CORRUPT`로 판정하고 기존 근거를 현재 승인에 쓰지 않는다.
- **REQ-CAN-003:** 수정은 기존 후보본을 덮어쓰지 않고 새 `parent_candidate_id`를 가진 자식 후보본에서 한다.
- **REQ-EVD-001:** 증거 원장은 이전 레코드 해시를 포함하는 append-only 해시 사슬이다.
- **REQ-EVD-002:** 원장 행의 수정과 삭제를 저장소 수준에서 거부한다.
- **REQ-EVD-003:** 참조 입력 변경은 새 무효화 사건으로 기록하며 과거 레코드를 고치지 않는다.
- **REQ-EVD-004:** 서로 다른 mission·revision·candidate의 증거를 합쳐 통과시키지 않는다.

### 상태 전이와 출시

- **REQ-POL-001:** 허용된 상태 전이만 수행한다.
- **REQ-POL-002:** `REVIEWING`·`APPROVED` 후보본의 내용을 같은 ID로 수정할 수 없다.
- **REQ-POL-003:** 필수 증거가 없거나 `STALE`·`REJECTED`이면 승인과 패키징을 거부한다.
- **REQ-POL-004:** 검토 실패는 기존 후보본을 불변으로 남기고 새 자식 후보본 작업으로 복귀시킨다.
- **REQ-REL-001:** 출시는 `출시`, `제한적 출시`, `보류`, `출시 금지`로 판정한다.
- **REQ-REL-002:** 제한적 출시는 범위·기한·되돌리기·제한 밖 경로 차단을 명시해야 한다.

## 4. 비기능 요구

- **REQ-NF-001:** Python 3.11 이상과 Windows에서 실행한다.
- **REQ-NF-002:** 핵심 상태와 해시는 같은 입력에서 결정론적으로 같다.
- **REQ-NF-003:** 스키마·정책·해시 검증에 실패하면 통과시키지 않는 방식으로 닫힌다.
- **REQ-NF-004:** 실제 명령·종료 코드·환경·해시를 기계 판독 가능한 형식으로 남긴다.
- **REQ-NF-005:** 단위 시험, 종단 시험, 결함 주입 시험을 자동 실행할 수 있다.

## 5. 최소 인수 시나리오

1. 모호한 목표는 탐색 경로와 방법·지표·편향 전문가를 포함한다.
2. 충분한 저위험 구현 목표는 불필요한 탐색 없이 제작 경로로 간다.
3. 연구 산출물은 여섯 비상쇄식 보증 단계를 모두 포함한다.
4. 다른 미션의 비동기 결과는 수신함에 격리되고 현재 단계가 바뀌지 않는다.
5. 사용자 지시 변경 뒤 이전 revision의 결과와 증거는 통과하지 못한다.
6. 후보본 입력 한 바이트 변경으로 기존 검토와 패키징이 무효화된다.
7. 검토자의 쓰기, 구현자의 오라클 수정, 자가 승인이 차단된다.
8. 원장 레코드 수정·삭제와 해시 사슬 변조가 탐지되거나 거부된다.
9. 검토 실패 뒤 새 자식 후보본에서만 수정할 수 있다.
10. 같은 candidate의 필수 증거가 모두 있을 때만 출시 판정을 만들 수 있다.
