# 동적 전문가 조직과 품질 보증 설계

## 1. 목적

이 설계는 LLM 에이전트를 사람 수만큼 단순 복제하는 것이 아니라, 소규모 회사 부서처럼 목표·구현·품질을 함께 책임지도록 구성한다. 세부 전문가 수는 고정하지 않는다. 먼저 과업에 필요한 관점을 빠짐없이 생성하고, 각 관점의 참여 깊이를 정한 뒤, 공통 지식과 역할 독립성을 기준으로 필요한 세부 전문가를 만든다.

기준 조사:

- `docs/enterprise-project-team-survey.md`
- `docs/agent-reliability-survey.md`

## 2. 상위 조직

### 2.1 요구·목적 책임 축

책임:

- 사용자 목적과 원하는 결과 정의
- 요구·제약·정상·경계·오류·악의적 사용 시나리오 작성
- 검증 가능한 품질 프로필 공동 작성
- 외부 사례와 도메인 의무 반영
- 프로그래밍·품질 보증 의견을 요구 기준선에 반영

최종 산출물:

- 목표 정의
- 요구 기준선
- 품질 프로필
- 검증 방법 초안
- 결정·가정·미해결 쟁점

### 2.2 프로그래밍·해결 책임 축

책임:

- 일반 컴퓨터공학과 소프트웨어 공학에 기반한 해결책 제시
- 기술 가능성·비용·운영·보안·유지보수성 검토
- 설계·구현·자체 시험·빌드·동결 후보본 작성
- 알려진 한계와 실패를 숨기지 않고 기록
- 합의된 요구와 품질 하한을 단독으로 낮추지 않음

최종 산출물:

- 기술 선택과 대안 비교
- 설계 기준선
- 코드·자체 시험·빌드 결과
- 동결 후보본
- 운영·기술 문서

### 2.3 검증·품질 보증 책임 축

책임:

- 요구 단계부터 측정 방법·오라클·반례·필요 증거 제안
- 결정론적 사실 검사와 분야별 의미 검증
- 결함이 품질 하한과 원하는 결과에 미치는 영향 판정
- 구현과 이해관계를 분리한 최종 품질 보증
- 통과·제한적 출시·보류·출시 금지 판정

최종 산출물:

- 독립 오라클
- 품질 항목별 관찰값과 하한 비교
- 재현 가능한 결함·영향·남은 위험
- 최종 품질 보증과 출시 판정

### 2.4 총괄 관리자

총괄 관리자는 네 번째 전문 부서가 아니다. 다음을 조정하는 정책 집행자다.

- 최신 사용자 목표와 revision 유지
- 관점 생성 누락·과도함 점검
- 세 책임 축이 공동 작성한 품질 프로필의 이상 여부 확인과 기준선 확정
- 역할·작업·후보본·증거·권한 결속
- 단계 전환과 실패 복귀
- 조사·기술개발 전환 및 자원 임계값 확인

총괄 관리자는 구현·검증·자가 승인·패키징을 대신하지 않는다.

## 3. 필수 관점 생성

### 3.1 기본 관점

모든 미션에서 최소한 다음 관점을 생성한다.

- 사용자 목적과 업무
- 일반 컴퓨터공학과 프로그래밍
- 필수 기능과 정확성
- 품질 보증과 시험 가능성
- 기본 보안·비밀정보·권한·입력 검증
- 자료 무결성·개인정보·법적 의무
- 사용성·접근성
- 성능·자원
- 운영·감시·복구
- 유지보수·의존성·공급망
- 사용자·기술·운영 문서
- 해당 과업의 도메인 지식
- 연구 방법·통계·평가지표 필요성
- 허용·금지 외부 효과

적용할 필요가 없다고 판단한 관점도 삭제하지 않는다. `not-applicable` 판정과 근거를 남긴다.

### 3.2 관점 추가 절차

1. 요구·목적 책임 축이 사용자·업무·법·도메인 관점을 제시한다.
2. 프로그래밍·해결 책임 축이 구조·자료·의존성·성능·운영·구현 위험을 제시한다.
3. 검증·품질 보증 책임 축이 시험 가능성·오라클·부정 사용·독립성·증거 위험을 제시한다.
4. 공식 기준과 유사 프로젝트 사례에서 추가 관점을 찾는다.
5. 총괄 관리자가 중복을 합치되 의미가 다른 관점을 삭제하지 않는다.
6. 모든 필수 관점에 담당 책임 축·품질 항목·산출물·검증 방법을 배정한다.

## 4. 관점 참여 프로필

P0~P5는 사람이나 전문가의 급수와 숙련도 등급이 아니다. P0~P3은 관점을 실제 작업에 적용하는 기본 심도이고, P4와 P5는 필요할 때 덧붙이는 독립 판정·조사 요건이다.

| 구분 | 뜻 | 적용 방식 |
|---|---|---|
| P0 | 자동 강제 | 결정론적 정책이나 자동 검사에 규칙, 입력, 기대 결과, 실패 처리를 명시한다. 별도 사람 전문가를 배정하지 않지만 담당 책임 축이 규칙과 실패를 책임진다. |
| P1 | 배정된 전문가가 담당 | 요구·프로그래밍·품질 보증에 이미 배정된 전문가가 통상 책임 범위에서 담당 산출물이나 판단을 처리하고 결과를 남긴다. |
| P2 | 지정 시점 자문 | 분야 전문가가 정해진 질문·입력·산출물·기한에 한해 참여한다. 해당 작업 단계 전체에 계속 참여하거나 최종 승인 권한을 얻지는 않는다. |
| P3 | 작업 단계 전반 참여 | 분야 전문가가 해당 작업 단계의 계획, 중간 판단, 산출물 작성·검토, 인계에 계속 참여한다. 자신이 만든 결과를 독립적으로 승인할 수는 없다. |
| P4 | 독립 판정 필요 | P0~P3의 기본 심도에, 구현과 분리된 권한·작업 공간·판정 기준을 가진 검토자를 추가한다. 검토자는 후보본이나 기대 결과를 수정할 수 없다. |
| P5 | 제한된 조사·연구개발 필요 | P0~P3의 기본 심도에, 질문·자료 범위·자원 한도·중단 조건·판단용 산출물을 정한 문헌 조사, 시제품 또는 실험을 추가한다. P5 자체는 승인 권한을 주지 않으며, 독립 판정이 필요하면 P4도 함께 지정한다. |

계획 자료에는 `delivery_depth: P0|P1|P2|P3`, `independent_assessment_required`, `bounded_investigation_required`를 별도 필드로 기록한다. `P3+P4`, `P2+P5+P4` 같은 표기는 이를 읽기 쉽게 줄여 쓴 것이다.

모든 적용 관점은 P0~P3 중 하나의 기본 심도를 가진다. 다음 요인을 각각 판단해 기본 심도, 독립 판정, 조사 필요 여부를 정한다.

- 필수 품질 하한 실패 영향
- 보안·안전·개인정보·재정·법적 위험
- 방법·기술의 불확실성
- 구현과 판정의 이해관계 충돌
- 규모·복잡성·운영 중요도
- 독립 오라클 필요성
- 외부 사례 부족
- 병렬 전문 검토의 기대 이익

## 5. 세부 전문가 구성

### 5.1 구성 순서

```text
목표
→ 필수 관점 전체 생성
→ 관점별 P0~P3 기본 심도와 P4·P5 추가 요건 결정
→ 공통 지식·단계·이해관계 분석
→ 관련 관점을 전문가 묶음으로 구성
→ 독립성이 필요한 묶음 분리
→ 전문가·권한·산출물·인계 계획 생성
```

### 5.2 묶을 수 있는 조건

- 같은 책임 축에 속함
- 같은 단계에서 작업함
- 분야 심화 지식의 공통 기반이 충분함
- 담당 관점의 품질 기준이 충돌하지 않음
- 한 전문가에게 맡겨도 문맥 과부하로 누락될 위험이 낮음

### 5.3 반드시 분리할 조건

- 구현과 최종 품질 판정
- 기대 결과 작성과 그 기대 결과에 맞추는 구현
- 승인과 패키징
- 같은 증거의 생산과 최종 유효성 판정
- 분야 지식이 실질적으로 달라 한 전문가가 근거 없이 추론해야 함
- 병렬 독립 검토가 필수 품질 하한에 필요함

전문가 수를 줄이는 작업은 필수 관점의 담당자·산출물·검증 방법이 모두 배정된 뒤에만 수행한다.

## 6. 전문가의 세 층 지식

각 세부 전문가는 지식 하나만 받지 않는다.

### 6.1 일반 방법 지식

예:

- 명료한 글쓰기와 구조화
- 출처 조사와 원문 검토
- 연구 질문과 비교 방법
- 논증·반례·불확실성 표시
- 협업·회의·의사결정 기록
- 정형 인계 작성

### 6.2 전문 영역 지식

반드시 일반 컴퓨터공학·소프트웨어 공학의 기반을 포함하고, 과업에 필요한 심화 지식을 추가한다.

예:

- 일반 소프트웨어 설계·자료 구조·알고리즘·시험
- 웹·자료·분산 시스템·운영
- 보안·암호·권한·위협 분석
- 수치 계산·통계·연구 방법·평가지표
- 해당 업무 도메인

보안 특화 지식은 일반 프로그래밍 기반을 대체하지 않는다. 일반 프로그램도 기본 보안 지식을 제거하지 않는다.

### 6.3 역할 판단 지식

예:

- 요구 전문가는 목표·검증 가능성·품질 수준을 판단
- 프로그래밍 전문가는 해결책의 적합성·비용·기술 위험을 판단
- 검증 전문가는 품질 하한·근거 충분성·남은 위험을 판단
- 조사 전문가는 출처 신뢰도·적용 가능성을 판단
- 출시 전문가는 적용 범위·운영 준비·되돌리기 가능성을 판단

## 7. 공통 지식 기반 소통

전문가 지식은 자유 문자열만으로 비교하지 않는다. 지식 항목에 `concept_id`, 이름, 판본, 출처, 적용 범위를 둔다. 보내는 전문가와 받는 전문가가 공유하는 개념 ID와 품질 항목을 `shared_foundation`으로 인계에 넣는다.

인계 문서에는 다음을 포함한다.

- 미션·revision·단계·작업·후보본
- 보내는 전문가와 받는 전문가
- 공통 개념·용어·품질 항목
- 입력 산출물 ID·경로·SHA-256
- 수행한 작업과 실제 결과
- 판단·대안·선택 이유
- 반영한 다른 책임 축의 의견
- 전제·불확실성·이견
- 미해결 사항과 품질 영향
- 다음 작업과 완료 기준

## 8. 인계 수락

모든 인계는 두 단계로 확인한다.

### 8.1 자동 검사

- JSON Schema
- 미션·revision·단계·작업·역할·후보본 결속
- 산출물 상대 경로와 허용 경로
- 파일 존재·일반 파일 여부·SHA-256
- 필수 입·출력 종류
- 권한 증표 유효성·사용 횟수

### 8.2 수신 전문가의 사용 가능성 확인

- 처음부터 다시 조사·작성하지 않고 이어 갈 수 있는가
- 자기 역할에 필요한 공통 개념과 품질 기준이 있는가
- 전제·이견·미해결 사항이 분명한가
- 잘못된 역할 겸임이나 이해관계 충돌이 없는가
- 필요한 자료가 빠졌다면 어느 품질 항목이 왜 부족한가

두 확인을 모두 통과해야 다음 작업을 시작한다. 인계 수락은 최종 품질 통과가 아니다. 검증·품질 보증 책임 축이 별도로 최종 판정한다.

## 9. 동적 품질 프로필

세 책임 축이 요구 작성 단계에서 공동으로 품질 프로필을 만든다.

- 요구·목적: 사용자 목적과 원하는 결과
- 프로그래밍·해결: 구현 가능성·비용·기술 제약
- 검증·품질 보증: 측정 방법·오라클·반례·필요 증거

총괄 관리자는 목표와 동떨어짐, 지나치게 낮은 하한, 과도한 요구, 내부 충돌을 확인한 뒤 기준선을 확정한다. 내용을 단독으로 다시 작성하지 않는다.

각 품질 항목은 다음을 가진다.

- `quality_id`
- 이름과 설명
- 원하는 결과에 대한 기여
- `mandatory-floor` 또는 `improvement-target`
- 측정 방법과 단위
- 하한 또는 목표값
- 필수 증거 종류
- 미달 영향
- 적용 범위
- 다시 검토할 변경 조건
- 주 책임 축과 독립 검증 역할

정확성·보안·자료 무결성·필수 기능과 과업별 핵심 품질은 비보상 하한이다. 하나라도 하한 미달이면 다른 장점으로 상쇄하지 않는다. 모든 필수 하한을 넘긴 뒤 사용성·유지보수성·성능 여유·문서성·운영 편의성을 원하는 결과 기여도로 종합 평가한다.

### 9.1 세 책임 축 공동 검토

세 책임 축은 최소한 다음 세 시점에 함께 검토한다.

1. 목표·요구·품질 계획: 필수 관점, 품질 하한, 검증 방법, 알려지지 않은 사항을 공동 작성한다.
2. 설계 준비: 프로그래밍 가능성, 품질 측정 가능성, 독립 오라클 준비 여부, 남은 이견을 확인한다.
3. 후보본 품질 검토: 구현 결과와 품질 항목별 근거, 잔여 위험, 출시 범위를 대조한다.

공동 검토는 자유 대화 기록만 남기지 않는다. 검토 ID, 참여 전문가와 책임 축, 입력 산출물과 해시, 각 축의 제안, 합의·이견, 채택 근거, 후속 작업과 담당자, 다음 통과 기준을 정형 기록으로 남긴다. 총괄 관리자는 검토를 조정하고 기록 누락을 확인하지만 전문 판단을 대신하지 않는다.

회의에서 `문제없음` 또는 `완료`라고 합의했더라도 실제 산출물·실행 영수증·품질 근거를 대신할 수 없다.

## 11. 이견·조사·기술개발

세 책임 축의 의견이 해결되지 않으면 사용자에게 즉시 넘기지 않는다.

1. 쟁점·영향·필요 정보를 기록한다.
2. 논문·공식 문서·대기업 기술 자료·신뢰받는 실무 자료를 조사한다.
3. 외부 사례와 현재 과업의 규모·전제·비용·보안·운영 차이를 평가한다.
4. 적용 가능한 방법을 작은 실험으로 확인한다.
5. 공개 해법이 부족하면 P5 연구·기술개발로 전환한다.
6. 문제·사례·실험·결과·선택·한계를 기술 글 형식으로 남긴다.

조사·기술개발은 기본적으로 자율 수행한다. OpenAI Codex Max x20 Plan 주간 한도의 10% 이상 또는 단일 세션 8시간 이상이 예상되면 시작 전에 계획서를 사용자에게 제출한다. 진행 중 임계 초과가 예상돼도 중단 후 계획서를 먼저 제출한다.

## 12. 허위 완료와 무실행 보고 차단

LLM의 `완료`, `pass`, `검증함` 문장은 상태 변경 권한이 없다.

완료 수준을 분리한다.

```text
에이전트 호출 종료
≠ 작업 시도 종료
≠ 산출물 제출
≠ 인계 수락
≠ 품질 검증
≠ 단계 완료
≠ 미션 완료
```

정책 엔진만 다음 근거를 확인해 상태를 바꾼다.

- 하네스가 발급한 작업·역할·권한 증표
- 실제 도구·프로세스 실행 영수증
- 실제 산출물과 SHA-256
- 단계별 필수 입·출력
- 자동 검사 결과
- 수신 전문가의 사용 가능성 확인
- 검증·품질 보증 책임 축의 품질 항목별 판정
- 현재 미션·revision·후보본과의 일치
- 미해결 차단 사항과 보상 대기 작업의 부재

조사 작업은 실제 URL·접근 정보·인용·비교·적용 가능성 평가가 있어야 한다. 실행 작업은 명령·환경·종료 코드·원시 출력·산출물 해시가 있어야 한다. 의미 판단은 품질 항목·관찰값·하한·영향·근거가 있어야 한다.

## 13. 재시도·체크포인트·완료 무효화

완료 전에는 일시적 오류에 대한 한도 있는 자동 재시도와 마지막 유효 체크포인트에서의 재개를 허용한다. 이미 검증된 하위 작업은 다시 수행하지 않는다.

완료 뒤 같은 입력·요구 기준선·후보본을 독립적으로 재확인했을 때 수정이나 재실행이 필요하면 기존 완료 판정을 무효화한다. 기존 사건을 삭제하지 않고 잘못된 완료 판정의 원인과 새 시도를 후속 사건으로 남긴다.

## 14. 시험 가능한 요구

### EXP-001 세 책임 축

모든 미션은 요구·목적, 프로그래밍·해결, 검증·품질 보증의 세 책임 축을 가져야 한다. 총괄 관리자는 어느 축도 겸하지 않아야 한다.

### EXP-002 필수 관점

모든 미션은 기본 관점 전체를 생성하고 각 관점에 적용·비적용 근거를 기록해야 한다.

### EXP-003 참여 프로필

모든 적용 관점은 P0~P3 중 하나의 기본 심도와 P4·P5 적용 여부를 가져야 한다. 각 값은 위험, 불확실성, 독립성 필요와 연결돼야 한다.

### EXP-004 전문가 묶음

세부 전문가는 공통 지식·단계·책임 축을 기준으로 관점을 묶어 생성해야 하며, 필수 관점이 담당자 없이 남아서는 안 된다.

### EXP-005 독립성

구현과 최종 판정, 기대값 작성과 구현, 승인과 패키징, 증거 생산과 최종 유효성 판정은 같은 권한 증표와 작업 공간으로 수행할 수 없어야 한다.

### EXP-006 세 층 지식

모든 세부 전문가는 일반 방법, 전문 영역, 역할 판단 지식을 모두 가져야 한다. 전문 영역에는 일반 컴퓨터공학 기반과 과업 심화 지식이 함께 있어야 한다.

### EXP-007 동적 품질 프로필

세 책임 축의 기여 없이 품질 기준선을 확정할 수 없어야 한다. 필수 품질 하한은 서로 상쇄할 수 없어야 한다.

### EXP-008 공통 지식 인계

인계는 공통 개념 ID·품질 항목·산출물 해시·판단·미해결 사항·다음 완료 기준을 포함해야 한다.

### EXP-009 이중 인계 수락

자동 검사와 수신 전문가의 사용 가능성 확인 중 하나라도 실패하면 다음 작업을 시작할 수 없어야 한다.

### EXP-010 조사·기술개발 전환

해결되지 않은 이견은 외부 사례 조사와 적용 가능성 평가를 거쳐야 하며, 공개 해법 부족 시 연구·기술개발로 전환해야 한다.

### EXP-011 자원 임계값

조사·기술개발의 예상 소모가 주간 한도 10% 또는 단일 세션 8시간 이상이면 계획서 승인 전 실행을 시작할 수 없어야 한다.

### EXP-012 허위 완료 차단

실제 필수 산출물·실행 영수증·인계 수락·품질 판정 없이 문자열 주장만 제출하면 작업·단계·미션이 진행되지 않아야 한다.

### EXP-013 완료 안정성

완료 전 재시도·체크포인트 재개는 허용하되 완료 후 독립 재확인에서 재작업이 필요하면 기존 완료 사건을 무효화해야 한다.

### EXP-014 외부 효과 중복 억제와 보상

모든 외부 쓰기는 안정적인 논리 작업 ID·중복 제거 키·결과 영수증에 결속해야 한다. 응답 유실 뒤 같은 작업을 다시 호출해도 새 효과가 생기지 않아야 하며, 이미 성공한 외부 효과 뒤 후속 작업이 영구 실패하면 등록된 보상 동작 또는 상태 대조 결과를 별도 증거로 남겨야 한다.

### EXP-015 검증자 편향과 불확실성 처리

의미 검증은 품질 항목별 독립 평가를 먼저 수행하고, 직접 비교가 필요하면 후보 순서를 바꾼 두 평가를 모두 기록해야 한다. 순서 교환에서 판정이 뒤집히거나 검증자 이견·낮은 신뢰도·분포 밖 사례가 있으면 자동 통과가 아니라 판정 보류 또는 상향 검토로 전이해야 한다. 같은 모델에 역할 이름만 다르게 준 여러 호출을 독립 검증자로 간주해서는 안 된다.

## 15. 필수 결함 주입 시험

- 시제품에서도 기본 보안 관점을 제거하면 계획 확정 거부
- 보안 프로그램에서 일반 프로그래밍 관점을 제거하면 계획 확정 거부
- 연구 프로그램에서 일반 프로그래밍·기본 보안·방법 타당성 중 하나를 제거하면 계획 확정 거부
- 구현자와 최종 검증자를 같은 전문가로 묶으면 전문가 구성 거부
- 세 층 지식 중 하나가 비면 역할 발급 거부
- 공통 개념이 없는 인계를 형식상 통과시키려 하면 거부
- 산출물 파일이 없거나 해시가 다르면 인계 거부
- 자동 검사는 통과하지만 수신 전문가가 필수 정보 누락을 지적하면 다음 작업 시작 거부
- 수신 전문가가 이유 없이 거부하면 거부 판정 자체를 수락하지 않음
- 필수 품질 하한 하나가 미달인데 개선 품질 점수로 상쇄하려 하면 출시 거부
- 비차단 결함이 있지만 필수 하한을 모두 충족한 결과를 무조건 실패시키면 판정 규칙 위반
- 실제 실행 없이 `pass` JSON만 제출하면 상태 진행 거부
- 완료 전 중단 뒤 체크포인트 재개 시 이미 검증된 하위 작업을 다시 실행하지 않음
- 체크포인트 저장이 실패했는데 성공처럼 계속하면 단계 완료 거부
- 계획된 종료에서는 현재 안전 경계의 체크포인트 저장을 확인한 뒤 같은 논리 실행 ID로 재개
- 외부 효과 성공 뒤 응답이 유실돼 같은 작업을 재호출해도 새 효과가 생기지 않고 기존 영수증을 반환
- 앞 단계 외부 효과 성공 뒤 후속 단계가 영구 실패하면 보상 또는 상태 대조 증거가 없을 때 완료 거부
- 완료 후 독립 재확인에서 재작업 필요가 확인되면 기존 완료 판정 무효화
- `(A, B)`와 `(B, A)` 비교에서 판정이 뒤집히면 자동 통과 거부
- 같은 모델에 역할 이름만 다르게 준 다수결로 독립 검증 요건을 충족하려 하면 거부
- 다른 미션·구 revision·다른 후보본의 인계·증거·권한 증표 주입 거부
- 조사·기술개발 예상치가 자원 임계값을 넘는데 계획서 없이 시작하면 거부
