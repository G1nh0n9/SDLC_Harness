# 실제 소프트웨어 조직의 역할 구성과 LLM 전문가 조직 적용안

## 1. 조사 목적

프로젝트마다 세부 전문가 수를 고정하지 않으면서도 일반 프로그래밍·품질·보안·운영 같은 기본 관점을 빠뜨리지 않으려면 어떤 조직 원칙이 필요한지 조사했다. 특히 다음 질문에 답한다.

- 실제 프로젝트팀은 보통 몇 명으로 구성되는가?
- 어떤 역할이 어떤 산출물을 만드는가?
- 모든 프로젝트에 필요한 기본 역량과 조건부 심화 역량은 무엇인가?
- 시제품·일반 프로그램·보안 프로그램·연구 프로그램에서 품질 깊이가 어떻게 달라지는가?
- 이를 요구·프로그래밍·검증의 세 책임 축과 동적 LLM 전문가로 어떻게 옮길 것인가?

## 2. 핵심 결론

### 2.1 고정 인원수가 정답은 아니다

공식 Scrum Guide는 교차 기능 팀이 보통 10명 이하이며, 이해관계자 협업·검증·유지보수·운영·실험·연구개발을 포함해 제품에 필요한 모든 일을 할 수 있어야 한다고 설명한다.[1] Amazon도 10명 미만의 소규모 팀을 예로 들지만 숫자 자체보다 한 제품이나 서비스의 전체 생명주기를 책임지는 데 초점을 둔다. 이를 위해 엔지니어링·시험·제품·프로그램 관리·운영 자원을 팀 안에 둔다.[9]

따라서 “일반 프로그램은 5명, 보안 프로그램은 9명” 같은 고정값을 하네스 규칙으로 만들면 안 된다. 대신 다음 두 값을 분리해야 한다.

1. 반드시 검토해야 하는 관점의 수
2. 그 관점을 담당하기 위해 실제로 생성하는 세부 전문가의 수

한 세부 전문가가 관련된 여러 관점을 충분히 다룰 수는 있지만, 관점 자체를 생략할 수는 없다.

### 2.2 특화 전문성은 일반 역량 위에 더한다

영국 정부의 디지털 서비스팀 안내서는 모든 팀이 사용자 요구 분석, 우선순위 설정, 설계·구현·시험·배포·운영, 보안 보호, 실제 사용자 시험, 성능 측정, 자료 처리 능력을 가져야 한다고 규정한다.[5] 단계가 바뀌면 역할과 인원은 달라진다. 발견 단계에도 개발자·자료 분석가·보안 전문가가 필요할 수 있고, 시제품 단계에는 제품·전달·연구·설계·개발·기술 리드·보안·접근성 역할과 품질·운영 전문성에 접근할 수 있어야 한다.[5]

이는 보안 프로그램에서 일반 프로그래밍 전문가를 제거하거나, 일반 프로그램에서 보안 관점을 제거하는 방식이 틀렸음을 뜻한다. 기본 역량은 항상 있고, 제품 특성에 따라 특정 분야의 깊이와 독립성을 높여야 한다.

### 2.3 품질은 전 팀의 책임이지만 독립 검토가 필요한 지점이 있다

영국 정부 안내서는 디지털 서비스의 품질이 전 팀의 책임이며, 침투 시험이나 품질 보증처럼 철저한 독립 검토가 필요한 경우 별도 전문성을 단기간 투입할 수 있다고 설명한다.[6] GitLab의 현재 공개 시험 안내서도 기능팀이 단위·통합·종단 시험의 설계·작성·유지·장애 분류를 소유하고, 자동 파이프라인·필수 코드 검토·배포 뒤 감시를 개발 흐름 전체에 넣는다. 별도 Developer Experience 조직은 일상 시험을 대신하지 않고 공용 기반과 깊은 전문성이 필요한 심각한 문제를 지원한다.[13]

LLM 하네스에는 이를 다음처럼 적용한다.

- 요구·프로그래밍·검증의 세 책임 축 모두 품질을 만드는 책임이 있다.
- 프로그래밍 책임 축이 자기 시험을 작성하고 실행해야 한다.
- 검증 책임 축은 같은 시험을 반복하는 사람이 아니라 품질 하한 충족 여부를 독립적으로 보증한다.
- 자동 검사로 판정 가능한 사실은 독립 LLM의 문장보다 먼저 확인한다.
- 보안·연구 방법·평가지표처럼 이해관계나 심화 지식이 중요한 항목은 별도 검증 전문가를 둔다.

### 2.4 기본 보안은 모든 개발 흐름에 포함하고 깊이는 위험에 맞춘다

Microsoft SDL은 보안 위험이 설계·코드·빌드와 배포·운영 어느 단계에서나 발생할 수 있으므로 보안 기준·위협 모델링·공급망·개발 환경·보안 시험·운영 감시·교육을 전체 개발 흐름에 통합한다.[2] NIST SSDF도 일반 개발 생명주기 대부분이 보안을 충분히 다루지 않으므로 안전한 개발 실천 사항을 각 방식에 추가해야 한다고 설명한다.[4]

다만 NIST는 SSDF를 모든 프로젝트에 똑같은 깊이로 적용하는 체크리스트로 보지 않는다. 사업·미션 요구, 위험 허용 범위, 자원, 비용, 실현 가능성과 적용 가능성에 맞춰 실천 사항을 조정하라고 한다.[3]

하네스는 다음 원칙을 사용해야 한다.

- 모든 프로그램에 기본 보안·자료 보호·의존성·비밀정보·권한·입력 검증 관점을 적용한다.
- 보안 제품이나 고위험 기능에는 위협 분석·공격 표면·권한 우회·부정 시험·침투 시험 전문가를 추가한다.
- 낮은 위험의 시제품에는 기본 보안 하한을 유지하되 고비용 공격 검증까지 자동으로 요구하지 않는다.
- “보안 전문가를 만들지 않았다”는 이유로 기본 보안 검토가 사라져서는 안 된다.

### 2.5 운영 전문성도 위험과 단계에 따라 참여 깊이가 달라진다

Google SRE의 공개 운영 준비 검토는 모든 서비스에 같은 수의 SRE를 배정하지 않는다. 문서와 자문으로 충분한 서비스가 있고, 새 기능의 상위 설계만 몇 시간 검토하는 1~2명 자문이 있으며, 운영 책임을 넘겨받을 서비스에는 보통 1~3명의 SRE가 서비스별 준비 검토를 수행한다.[10] 중요도·규모·복잡성이 높으면 SRE가 설계 단계부터 조기 참여한다.[10]

운영 뒤에도 서비스 특성에 따라 개발자나 SRE가 당직을 맡고, 사고 대응·경보·부하·후속 수정을 조정한다.[11] 따라서 운영 전문가 역시 항상 별도 인원으로 생성할 필요는 없지만, 운영 관점 자체는 설계와 품질 프로필에서 빠지면 안 된다.

## 3. 실제 조직에서 반복되는 기본 역할과 산출물

조직마다 이름은 다르지만 공개 자료에서 다음 책임이 반복된다. 영국 정부 서비스팀은 제품 관리자·서비스 책임자·전달 관리자·사용자 연구자·콘텐츠 설계자·설계자·개발자를 기본으로 두고, 규모와 복잡성에 따라 성능 분석·기술 설계·운영·업무 분석·품질·기술 문서 역할을 추가한다.[6] GitLab은 기능·유지보수·사용성·성능·취약점·가용성·시험 문제의 결정 책임자를 분야별로 나누고, 결정과 근거를 공개 기록으로 남기도록 한다.[12]

| 책임 영역 | 대표 역할 | 핵심 산출물 |
|---|---|---|
| 목적·가치 | 제품 책임자, 서비스 책임자 | 제품 목표, 우선순위, 성공 지표, 범위 |
| 사용자·업무 이해 | 사용자 연구, 업무 분석, 도메인 전문가 | 사용자 요구, 업무 규칙, 연구 결과, 적용 범위 |
| 설계 | 제품·서비스·상호작용 설계, 기술 설계 | 사용자 흐름, 구조 결정, 자료·인터페이스 명세 |
| 일반 소프트웨어 공학 | 개발자, 기술 리드 | 코드, 단위·통합 시험, 빌드, 기술 결정 기록 |
| 품질 보증 | 품질 책임자, 시험자, 분야별 검증자 | 품질 프로필, 시험 전략, 결함·위험 판정, 출시 판정 |
| 보안·자료 보호 | 보안 책임자, AppSec, 개인정보·법무 | 보안 요구, 위협 분석, 부정 시험, 위험 수용 기록 |
| 운영·신뢰성 | DevOps, SRE, 운영자 | 배포·감시·경보·복구·용량·장애 대응 자료 |
| 성능·자료 | 성능 분석가, 자료 전문가 | 성능 기준, 측정 결과, 자료 품질·계보 |
| 문서·전달 | 콘텐츠 설계, 기술 문서 | 사용자·API·운영·구조 문서, 변경 안내 |
| 진행·조정 | 전달 관리자, 프로그램 관리자 | 작업 계획, 의존성, 차단 사항, 의사결정 기록 |

Atlassian은 제품 개발을 아이디어 생성에서 시험·출시·실제 고객 전달까지 이어지는 여러 단계의 과정으로 설명하고, 제품 복잡성과 자원에 따라 기간과 수행 방식이 달라진다고 본다.[7] GitLab 제품 안내서도 제품 자체뿐 아니라 웹사이트·가격·문서·영업·지원까지 이어지는 전체 경험과 고객 문제를 함께 고려해야 한다고 강조한다.[8]

따라서 하네스의 결과물도 코드에 한정하면 안 된다. 목표·요구·검증 방법·설계·코드·시험·운영·문서가 목표에 필요한 범위만큼 함께 나와야 한다.

## 4. 단계에 따른 역할 참여 깊이

사람 조직에서는 한 사람이 여러 역량을 겸하거나 전문 조직에서 잠깐 지원받는다. LLM 하네스에서는 이를 하나의 서열이 아니라 `관점 참여 프로필`로 표현하는 편이 정확하다.

| 구분 | 적용 방식 | 사람 조직의 예 | LLM 하네스 동작 |
|---|---|---|---|
| P0 자동 강제 | 결정론적 규칙으로 전부 판정 | 조직 공통 기준·자동 도구 | 규칙·입력·기대 결과·실패 처리를 정책으로 실행 |
| P1 배정된 전문가가 담당 | 이미 배정된 책임자가 통상 업무로 처리 | 일반 개발자의 기본 보안·시험 책임 | 기존 전문가 프로필에 관점·산출물·판단 방법을 명시 |
| P2 지정 시점 자문 | 한정된 쟁점에 분야 전문가 참여 | 보안·성능·SRE 단기 자문 | 질문·입력·산출물·기한을 정해 별도 전문가가 답변 |
| P3 작업 단계 전반 참여 | 해당 작업 단계에 계속 참여 | 팀에 포함된 보안·자료·운영 전문가 | 별도 전문가가 계획·중간 판단·산출물·인계에 참여 |
| P4 독립 판정 추가 | 생산자와 이해관계를 분리해 판정 | 침투 시험·독립 검토·감사 | P0~P3에 별도 권한과 작업 공간을 가진 검토자 추가 |
| P5 제한된 조사·연구개발 추가 | 알려진 답이나 근거가 부족함 | 연구팀·실험팀 | P0~P3에 범위·자원·중단 조건이 정해진 조사나 실험 추가 |

모든 적용 관점은 P0~P3 중 하나를 기본 심도로 가진다. 필수 품질 하한에 독립 판정이 필요하면 P4를 추가하고, 공개된 해법이나 근거가 부족하면 P5를 추가한다. P5 결과도 독립 판정이 필요하면 P4를 함께 둔다.

## 5. 프로젝트 유형별 예시

### 5.1 빠른 시제품

목표는 지정된 최적 조건에서 핵심 가설과 동작을 빠르게 확인하는 것이다.

- 기본: 목적·사용자, 일반 프로그래밍, 검증, 기본 보안, 간단한 사용·실행 문서
- 품질 하한: 지정 입력에서 핵심 동작, 반복 실행 가능, 허용하지 않은 외부 효과 없음, 한계 명시
- 낮춰도 되는 깊이: 광범위한 호환성, 고부하 운영, 드문 오류 복구, 장기 유지보수
- 결과물: 가설, 시제품, 실행 절차, 실제 결과, 적용 한계, 다음 판단

전문가 수를 줄이더라도 기본 관점을 제거하지 않는다. 한 세부 전문가가 일반 구현·기본 보안·간단한 시험을 함께 맡을 수 있다.

### 5.2 일반 업무 프로그램

- 기본: 제품·업무 요구, 사용자 관점, 일반 설계·프로그래밍, 품질 보증, 기본 보안·자료 보호, 운영·문서
- 품질 하한: 정상·경계·일반 오류 처리, 자료 무결성, 기본 권한·입력 검증, 유지 가능한 코드, 배포·복구 가능
- 조건부 심화: 높은 트래픽이면 성능·SRE, 민감 자료면 개인정보·보안, 복잡한 사용자 흐름이면 연구·접근성
- 결과물: 요구 기준선, 품질 프로필, 설계, 코드·시험, 운영·사용 문서, 출시 판정

### 5.3 보안 프로그램

일반 프로그래밍 역량을 그대로 유지하면서 보안 관점의 참여 깊이를 높인다.

- 추가 요구 전문성: 자산·공격자·오용 사례·법적 요구
- 추가 프로그래밍 전문성: 보안 구조·암호·권한·비밀정보·공급망
- 추가 검증 전문성: 위협 기반 시험·퍼징·침투·권한 우회·로그 검토
- 품질 하한: 악의적인 입력과 우회 시도에 강건함, 기본 거부, 최소 권한, 재현 가능한 부정 시험
- 결과물: 위협 분석, 보안 요구, 공격 표면, 보안 시험·지적·완화, 남은 위험

### 5.4 논문·연구 프로그램

일반 프로그래밍·보안·운영 역량을 유지하면서 연구 방법과 재현성 관점의 참여 깊이를 높인다.

- 추가 요구 전문성: 연구 질문·추정 대상·자료 생성 과정·승인 범위
- 추가 프로그래밍 전문성: 알고리즘·수치 계산·실험 자동화·계보
- 추가 검증 전문성: 방법 타당성·의미 일치·평가지표 독립 검산·실험 무결성·재현성
- 품질 하한: 과학적으로 검증 가능하고 질문에 타당한 방법, 원자료에서 표·그림까지 재생성 가능한 계보
- 결과물: 방법 결정, 수식·의사 코드·실행 코드 연결, 실험 계획·원시 결과, 독립 검산, 재현 묶음

## 6. LLM 하네스의 세 책임 축으로 재구성

### 6.1 요구·목적 책임 축

기본 지식:

- 목표 발견과 요구 작성
- 사용자·업무·도메인 이해
- 글쓰기·조사·논증
- 품질 프로필과 검증 가능성
- 기본 보안·안전·자료·운영 요구 점검

동적 심화 전문가:

- 사용자 연구, 법무·정책, 보안 요구, 자료·통계, 연구 방법, 접근성, 운영 목표

핵심 산출물:

- 목표 정의
- 요구 기준선
- 동적 품질 프로필
- 정상·경계·오류·악의적 사용 시나리오
- 검증 방법의 초안

### 6.2 프로그래밍·해결 책임 축

기본 지식:

- 일반 컴퓨터공학과 소프트웨어 공학
- 설계·구현·시험·빌드
- 기본 보안 코딩과 자료 무결성
- 운영 가능성과 유지보수성
- 기술 문서 작성

동적 심화 전문가:

- 프론트엔드·백엔드·자료·분산 시스템·암호·성능·SRE·수치 계산·특정 도메인

핵심 산출물:

- 기술 선택과 비교
- 설계 기준선
- 코드와 자체 시험
- 동결 후보본
- 실행·빌드·운영 자료
- 알려진 한계

### 6.3 검증·판단 책임 축

기본 지식:

- 품질 보증과 시험 설계
- 실제 산출물·명령·해시 검산
- 요구·구현 의미 일치
- 기본 보안·성능·사용성·운영 검토
- 결함의 품질 영향 판정

동적 심화 전문가:

- AppSec·침투 시험·성능·접근성·통계·평가지표·재현성·운영 준비·법규

핵심 산출물:

- 독립 오라클
- 품질 항목별 관찰값과 하한 비교
- 재현 가능한 결함과 영향
- 통과·제한적 출시·보류·출시 금지 판정
- 남은 위험과 다시 검토할 조건

## 7. 세부 전문가 생성 규칙

### 7.1 먼저 관점을 생성한다

하네스는 곧바로 전문가 수를 정하지 않는다. 먼저 다음에서 가능한 관점을 모은다.

1. 사용자 목표와 결과
2. 품질 속성: 정확성·성능·안정성·보안·자료 무결성·유지보수성·사용성·접근성·재현성·운영성
3. 자료와 외부 효과
4. 법·조직·도메인 의무
5. 정상·경계·오류·악의적 사용
6. 의존성·배포·운영 환경
7. 연구·통계·평가지표 필요성
8. 각 책임 축이 독립적으로 제시한 위험과 기회
9. 공식 기준과 유사 프로젝트 사례

### 7.2 관점별 참여 프로필을 정한다

각 관점마다 P0~P3 기본 심도를 정한다. 기본 보안처럼 항상 필요한 관점도 P0 자동 강제나 P1 책임자 담당으로 명시해야 한다. 더 깊은 전문 판단이 필요하면 P2 또는 P3을 고른다. 구현과 판정을 분리해야 하면 P4를 추가하고, 공개된 해법이나 근거가 부족하면 P5를 추가한다.

### 7.3 그다음 세부 전문가를 묶는다

공통된 심화 지식과 같은 단계·같은 이해관계를 가진 관점은 한 전문가가 함께 맡을 수 있다. 다음 조건에서는 분리한다.

- 필요한 분야 심화 지식이 실질적으로 다름
- 구현과 최종 판정처럼 이해관계가 충돌함
- 필수 품질 하한의 독립 검증이 필요함
- 한 전문가가 맡으면 문맥이 지나치게 커져 누락 위험이 높음
- 병렬 조사가 시간과 품질을 개선함

전문가 수를 줄이는 최적화는 모든 필수 관점에 담당자·산출물·검증 방법이 배정된 뒤에만 수행한다.

## 8. 권고하는 기본 조직

사람 수를 흉내 내기보다 다음을 `최소 책임 구조`로 둔다.

```text
총괄 관리자
│
├─ 요구·목적 책임 축
├─ 프로그래밍·해결 책임 축
└─ 검증·판단 책임 축
```

각 축에는 작업 단계마다 최소 한 명의 책임 전문가가 존재한다. 그러나 이것이 세 명만 쓴다는 뜻은 아니다. 품질 프로필과 관점 참여 프로필에 따라 세부 전문가를 추가한다.

모든 세부 전문가는 다음 세 층의 지식을 함께 가진다.

1. 넓은 일반 방법 지식: 글쓰기·조사·연구·논증·인계
2. 분야 심화 지식: 일반 컴퓨터공학을 바탕으로 과업·보안·통계·운영 등 필요한 심화 분야
3. 역할 판단 지식: 요구 작성·구현 선택·품질 보증 등 맡은 책임에 맞는 판단

특화 지식은 일반 컴퓨터공학과 기본 품질 지식을 대체하지 않고 추가한다.

## 9. 전문가 사이의 인계

전문가 간 소통은 단순 요약문이 아니라 다음을 전달한다.

- 공통 분야 개념과 용어
- 목표와 품질 항목
- 입력 산출물 ID와 해시
- 합의된 전제와 판단 기준
- 수행한 작업과 실제 결과
- 다른 책임 축에서 반영한 의견
- 미해결 쟁점과 영향
- 다음 전문가가 해야 할 작업과 완료 기준

인계를 받는 전문가는 자료를 다시 만드는 사람이 아니라, 유효한 근거를 확인하고 자기 역할의 심화 판단을 이어서 추가한다.

모든 인계는 두 단계로 수락한다. 먼저 정책 엔진이 문서 형식, 미션, revision, 작업, 후보본, 산출물 경로와 SHA-256을 검산한다. 그다음 수신 전문가가 자료를 처음부터 다시 조사하거나 작성하지 않고 자기 작업을 이어 갈 만큼 충분한지, 품질 프로필의 필수 정보가 있는지, 잘못된 전제나 역할 간 충돌이 없는지 확인한다.

자동 검사와 수신 전문가 확인을 모두 통과해야 인계를 수락하고 다음 작업을 시작한다. 수신 전문가가 거부할 때는 부족한 품질 항목, 필요한 자료, 재작업 범위를 명시해야 한다. 인계 수락은 최종 품질 통과가 아니며, 검증·판단 책임 축이 품질 프로필에 따라 별도로 최종 품질을 보증한다.

## 10. 사용자와 합의한 전문가 구성 기준

1. `전문가 수 생성기`보다 먼저 `관점 목록 생성기`를 만든다.
2. 모든 미션에 일반 프로그래밍·품질·기본 보안·자료 무결성·운영·문서 관점의 최소 적용을 보장한다.
3. 품질 프로필에서 관점별 P0~P3 기본 심도와 P4·P5 추가 요건을 결정한다.
4. 세 책임 축이 각자 누락 가능성을 독립적으로 제시하고 공동 품질 계획을 만든다.
5. 총괄 관리자는 목표와 품질 수준의 이상 여부만 확인하고 기준선을 확정한다.
6. 공통 심화 지식을 기준으로 관점을 세부 전문가에게 묶되 독립 판정이 필요한 역할은 분리한다.
7. 각 전문가의 완료는 담당 관점에 필요한 산출물과 품질 기여가 확인될 때만 인정한다.
8. 새 정보가 나오면 전문가 수를 고정하지 않고 관점 수준과 역할 구성을 다시 계산한다.
9. 공개 사례가 부족하면 조사·기술개발로 전환하고 합의한 자원 임계값을 적용한다.
10. 제품 유형 예시는 초기 자료일 뿐, 실제 목표·위험·법·자료·운영 환경에서 품질 프로필을 생성한다.

이 방식을 하네스의 전문가 구성 기준으로 확정했다. 필수 관점을 먼저 모두 생성하고 P0~P3 기본 심도와 P4·P5 추가 요건을 정한 뒤, 공통 일반 지식·분야 심화 지식·작업 단계·이해관계를 기준으로 관점을 묶어 필요한 세부 전문가만 만든다. 구현과 독립 판정처럼 이해관계가 충돌하는 역할은 공통 지식이 많아도 분리한다. 새 위험이나 정보가 생기면 기존 전문가 명단을 그대로 유지하지 않고 관점 목록과 참여 프로필부터 다시 계산한다.
